# "How I Learned to Stop Worrying and Love the Mechanical Hook" (Claude Code, with Merlin Mann)

Speaker and standing: the gist is bylined "By Claude Code (Anthropic), with vague assistance from Merlin Mann", dated April 7, 2026. Merlin Mann is a known productivity writer and podcaster (43 Folders, Back to Work). The text is the model writing about its own work in the first person, so it is a first-hand report of about five months of use by one named person, but his part is not separable from the model's. Counts as trusted only weakly: a named, sustained user, no authored tool in this field, and all the numbers are self-reported and unverifiable by us. Recorded because it is the most detailed account found of a hook-heavy setup that names failures and compares instructions with hooks.

How read: raw gist fetched from gist.githubusercontent.com and read in full.

- Problem: over months he wrote "approximately 140,000 words of documentation", "One hundred and twenty explicit rules", a 253-line instruction file, a Pre-Response Checklist "I followed it about 30% of the time"; "The recurrence rate on documented problems ranged from 24% to 86%." A session ran `tccutil reset All` on his Mac, revoking every privacy permission. "knowing and doing are different operations, and only one of them is deterministic."
- Claims: "fifteen hooks" built "over five months and hundreds of sessions". "An internal audit scored 166 sessions across five behavioral dimensions and found that rules written as prose in instruction files achieved 25–40% compliance. The same rules, rewritten as hooks that block the response (exit code 2), achieved approximately 95% compliance." The instruction file went from 253 to 131 lines; what remains is "judgment calls that can't be mechanized". The scoring method is not described; no data is included.
- Hooks named, with the page's own effectiveness estimates: block-destructive.sh (PreToolUse, blocks `git push --force`, `git reset --hard`, untargeted `tccutil reset`, `rm -rf /` and more; "Zero false positives in production", 24 test assertions); check-claims.sh (Stop; blocks a response containing any of 79 banned phrases such as "I can't access", "from memory"; "1,480 blocks logged"); verify-claims.sh (Stop; a "breadcrumb" hook logs research tool calls on PreToolUse and blocks a confident factual claim if none was logged; 92 blocks); auto-commit.sh (PostToolUse and SessionEnd, non-blocking; born from "225 files sat uncommitted"); session-start.sh (SessionStart; git sync, handoff, tool manifest, test suite silent if green; context pre-loading "costs about 1–2% of the context budget").
- Blocking versus advising: "Blocking hooks: ~95% effective. Advisory hooks: ~40–60% — better than documentation, worse than blocking." "If you're not willing to block (because false positives would be too disruptive), accept 40–60% compliance and plan accordingly." Baseline failure rate "dropped from roughly one serious failure per four sessions to one per twenty or more".
- Design lessons: "Start with the incident" ("Don't write hooks for hypothetical problems"). "Test your hooks. Our first Stop hook used exit code 1 instead of exit code 2. It ran for weeks as a no-op before an audit caught the bug." (This is a fail-open case: exit 1 does not block.) Phrase-matching on model output "works" but is reactive: "they catch me after I've composed a bad response"; a residual failure (confident wrong answers with no banned phrase) is called unsolved, "reduced by maybe 70%".
- Source of the idea: credits Simon Willison with "deterministic mechanical constraints beat probabilistic behavioral instructions". The essay puts in quotation marks, as "Willison's formulation", the line "Advisory is theater. Either make it exit 2 or accept the variance." I could not find that sentence in Willison's posts I searched (his tag page, guide index and site search returned nothing about hooks), and the essay links only his pieces on testing, not on hooks. Treat the attribution as unverified; the sentence is at best this essay's wording.

Unverified: every figure. Effectiveness percentages are labelled "estimated". Stop-hook blocks that force regeneration are counted as saves, which is not the same as outcomes improved; no false-positive rate for the Stop hooks is given. Some judgment rules remain in the instruction file beside the hooks.
