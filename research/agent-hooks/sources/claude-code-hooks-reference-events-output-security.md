# Claude Code hooks reference: events, blocking, context injection, output caps, async, scope and security

Read in full as raw page text (curl, html.parser to text, about 214 KB), then searched and read the sections named below. Not read via WebFetch. The Stop, PreToolUse, timeout and exit-code mechanics for the test-gate use are in the sibling note [claude-code-hooks-reference-stop-and-pretooluse](../../hooks-as-test-gate/sources/claude-code-hooks-reference-stop-and-pretooluse.md); this note records the parts that matter for the other uses.

- Definition: "Hooks are user-defined shell commands, HTTP endpoints, MCP tool calls, LLM prompts, or subagents that execute automatically at specific points in Claude Code's lifecycle." The same events fire in the terminal, IDE extensions, the Desktop app and cloud sessions.
- Three cadences: per session (SessionStart, SessionEnd), per turn (UserPromptSubmit, Stop, StopFailure), and on every tool call in the agentic loop (PreToolUse, PostToolUse). The events table lists many more (PostToolUseFailure, PostToolBatch, Notification, SubagentStart, InstructionsLoaded, ConfigChange, CwdChanged, FileChanged, PreCompact, PostCompact, PreModelSwitch, Elicitation, WorktreeCreate, MessageDisplay and others).
- Handler types: command, http, mcp_tool, prompt (single LLM call) and agent (multi-turn, "experimental and may change").
- Which events can block, per the exit-code-2 table. Can block: PreToolUse, UserPromptSubmit, Stop, SubagentStop, PostToolBatch (stops the agentic loop before the next model call), PreCompact, ConfigChange (except policy_settings), TaskCreated, TaskCompleted, Elicitation. Cannot block: PostToolUse ("Shows stderr to Claude; the tool already ran"), PostToolUseFailure, Notification ("Exit code and stderr are ignored"), SessionStart ("Shows stderr to user only"), SessionEnd, InstructionsLoaded, StopFailure, CwdChanged, FileChanged, PostCompact, PermissionRequest for exit code 2 (a JSON decision object must be used instead).
- Non-blocking failures: for most events exit 1, unparseable or schema-invalid JSON, plain-text stdout, and a script that cannot start (for example a path that is mistyped or not executable, exit 127) all let the action proceed. The page says: "When you set up a policy hook, watch for this notice on its first run: a mistyped path in settings.json leaves the gate silently disabled." "For most hook events, exit code 2 is the only exit code that blocks through the code alone."
- Timeouts: on most events a timed-out hook renders no decision. A timed-out command, http or mcp_tool PreToolUse hook does not block the call ("don't count on a stalled hook to act as a gate"). A UserPromptSubmit hook that times out has its output, including additionalContext, discarded and the prompt still reaches Claude without it.
- Context injection: `additionalContext` "passes a string from your hook into Claude's context window". Claude Code wraps it in a system reminder and inserts it where the hook fired: SessionStart and SubagentStart at the start of the conversation, UserPromptSubmit alongside the prompt, PreToolUse/PostToolUse/PostToolBatch next to the tool result, Stop at the end of the turn. When several hooks return it, Claude receives all values. Uses the page lists: environment state, conditional project rules, external data. "For instructions that never change, prefer CLAUDE.md. It loads without running a script and is the standard place for static project conventions." The page advises factual phrasing: "Text framed as out-of-band system commands can trigger Claude's prompt-injection defenses, which causes Claude to surface the text to you instead of treating it as context."
- Staleness of injected context: for mid-session events, on `--continue` or `--resume` the saved text is replayed "rather than re-running the hook for past turns, so values like timestamps or commit SHAs become stale". SessionStart hooks run again on resume (source "resume" or "fork").
- Output caps: additionalContext, systemMessage, initialUserMessage and plain stdout are capped at 10,000 characters each. Over the cap, the output goes to a file and Claude sees the path and the first 2,000 characters; "Claude Code doesn't ask Claude to read the file". There is no setting to raise the cap.
- PostToolUse `updatedToolOutput` changes only what Claude sees: "The tool has already run by the time the hook fires, so any files written, commands executed, or network requests sent have already taken effect. Telemetry ... captures the original output before the hook runs. To prevent or modify a tool call before it runs, use a PreToolUse hook instead."
- A separate `classifierContext` field on PostToolUse (for auto-mode classifier notes) is capped at 2,000 characters per tool call, is treated as unverified context, and is ignored from background hooks. Not otherwise summarised here.
- Notification: exit code and stderr are ignored. Hooks run without a controlling terminal; to ring a bell or send a desktop notification a hook returns a `terminalSequence` field (allowlisted OSC and BEL sequences), which is written only in an interactive session and ignored with `-p` and in the Agent SDK.
- Async: `async: true` runs a hook in the background without blocking; output arrives on the next turn; "There is no deduplication across multiple firings of the same async hook." `asyncRewake` wakes Claude on exit 2 for long-running background failures.
- Parallelism: matching hooks run in parallel; for PreToolUse the most restrictive decision wins (deny, defer, ask, allow) and text from every hook is kept. One hook's deny does not stop sibling hooks from running (guide note). If several PreToolUse hooks rewrite input with `updatedInput`, the last to finish wins, so order is non-deterministic.
- Scope and who can turn hooks off: sources are user settings, project settings (committable), local settings, managed policy settings, plugins, and skill or subagent frontmatter. "Hooks from settings files, managed policy settings, and plugins also run inside subagents ... the input carries the agent_id and agent_type". `disableAllHooks` set in user, project or local settings cannot disable managed hooks; "There is no way to disable an individual hook while keeping it in the configuration." `allowManagedHooksOnly` (administrators) blocks user, project, local and plugin hooks, except plugins force-enabled by managed settings. Cloud sessions do not read local `~/.claude/settings.json`.
- Security: "Command hooks execute shell commands with your full user permissions. They can modify, delete, or access any files your user account can access." Claude Code holds back hooks from every settings file until the workspace trust dialog is accepted in interactive sessions, but in `-p` or SDK sessions "never shows the dialog and treats the folder as trusted, so hooks committed in a repository's .claude/settings.json run in a folder you've never trusted".
- Hooks and permission modes (guide page): PreToolUse hooks fire before the permission check in every mode; a deny blocks even with `--dangerously-skip-permissions`; an allow does not override deny rules from settings. So hooks "can tighten restrictions but not loosen them".
- Shell profile output: plain echo lines from a profile prepend to stdout and break JSON parsing (troubleshooting text in the guide).
