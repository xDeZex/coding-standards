# What belongs in AGENTS.md, a skill or a hook: findings

Scope: evidence gaps only. How the files are read, sized and layered is already in [the conventions conclusion](../agents-md-conventions/conclusion.md) and its sources (for example [Claude Code memory](../agents-md-conventions/sources/claude-code-memory.md), [Codex](../agents-md-conventions/sources/codex-agents-md.md), [Claude Code skills](../agents-md-conventions/sources/claude-code-skills.md)); the testing loop and hook-as-gate material is in [the testing conclusion](../testing-feedback-loop/conclusion.md). This note adds what those did not cover. Most of the studies below are preprints found through abstract pages read by a summarising tool; each source note says how much was actually read.

## Do context files help at all

The one substantial controlled study, [Gloaguen et al.](sources/gloaguen-evaluating-agents-md.md) (SWE-bench plus 138 real issues from repos with committed files, four agents), finds that context files do not generally improve task success, raise cost by over 20%, and that agents do follow them. LLM-generated files were marginally negative on success, developer-written files marginally positive (not significant). Repository overviews did not help agents find the relevant files sooner. The authors say such files are useful for non-standard practices and should hold only what is not already in the README. Two smaller studies point the same way on correctness: [Khatri](sources/khatri-context-files-two-agent-ablation.md) (17 tasks, 3 repos, effect bounded within about 10 to 15 points). On efficiency the studies disagree: [Lulla et al.](sources/lulla-agents-md-efficiency.md) report lower runtime (-28.6%) and output tokens (-16.6%) with an AGENTS.md at comparable completion, on 10 repos and 124 PRs. The disagreement is unexplained. All are Python or small-sample or abstract-only reads, and none is peer reviewed as far as the pages show. [Agent READMEs](sources/agent-readmes-context-files-empirical.md) is descriptive only: test procedures are the most common content of real files (75.9% of 2,303).

## Short and non-inferable

The three vendors converge, always as assertion without data. Anthropic: include what Claude cannot infer from code, cut any line whose removal would not cause a mistake, and expect an over-long file to be partly ignored ([best practices](sources/claude-code-best-practices-claude-md.md)); under 200 lines ([features overview](sources/claude-code-features-overview.md)). OpenAI: short and accurate beats long and vague, and add to it after the same mistake twice ([Codex](sources/codex-best-practices.md)). GitHub: no more than two pages, not task specific ([Copilot](sources/github-copilot-repository-instructions.md)). The "non-inferable" rule has empirical backing in Gloaguen (overviews and duplicated README content did not help; with other docs removed, generated files helped by 2.7%), but that study did not test which individual human-written lines matter.

## Does length reduce adherence

Vendor claim: yes ([Anthropic](sources/claude-code-best-practices-claude-md.md)). Measured in real Claude Code sessions, a [factorial study](sources/instruction-adherence-config-files-factorial.md) of 1,650 sessions found no detectable effect of file size, instruction position, file architecture or adjacent-file contradictions, but a drop in compliance of about 5.6% in odds per additional function generated within a session. Gloaguen also found no dependence of success or cost on file length. In the synthetic [IFScale](sources/ifscale-instruction-density.md) benchmark, adherence falls as the number of instructions rises (68% at 500 for the best model) with a bias toward earlier instructions; that is keyword rules in report writing, far from a short AGENTS.md. So the evidence for "shorter is followed better" is vendor assertion plus a synthetic benchmark; the one agentic test found no effect at the sizes it used (range not read). Evidence that a standing instruction decays over a long session comes from one abstract.

## Skills versus always-loaded instructions

First-party guidance describes the mechanism consistently: skills load only name and description up front, the body when the agent judges it relevant, further files on demand ([Anthropic blog](sources/anthropic-agent-skills-engineering-blog.md), [authoring guide](sources/anthropic-skills-authoring-best-practices.md), [features overview](sources/claude-code-features-overview.md)). Its stated placement rule is: always-needed facts and "always do X" rules in CLAUDE.md; sometimes-needed reference material and repeatable or invocable workflows in a skill; anything that must happen every time in a hook. Skill selection depends on the description, and the docs warn of missed or wrong skills.

Measured evidence is thin and cuts against relying on invocation. [Vercel](sources/vercel-agents-md-outperforms-skills.md) (vendor blog, one framework, one task type) found a skill went unused in 56% of cases by default (pass rate 53%, same as baseline), 79% with explicit instructions to use it, versus 100% for a compressed docs index in AGENTS.md. [SkillsBench](sources/skillsbench-benchmark.md) finds curated skills raise pass rate 33.9% to 50.5% and that two to three focused skills beat larger sets, with unverified snippets noting rarely invoked skills and poor descriptions; the [in-the-wild benchmark](sources/skills-in-the-wild-benchmark.md) finds the gain shrinks toward zero when the agent must find skills in a large pool. Neither Vercel nor these benchmarks involve test-running instructions.

## The claim "test-running instructions are better in a skill than AGENTS.md"

No evidence found for it, and no measurement that compares the two for this purpose. What exists points elsewhere or is silent:

- All three vendors put test and build commands in the always-loaded file: Claude Code lists "testing instructions and preferred test runners" among things to include and its example says "Prefer running single tests" ([best practices](sources/claude-code-best-practices-claude-md.md)); the features page says "build commands, test conventions" belong in CLAUDE.md; [Codex](sources/codex-best-practices.md) lists "Build, test, and lint commands" and "how to verify work"; [Copilot](sources/github-copilot-repository-instructions.md) lists the test steps. Skills are recommended for repeated multi-step workflows (a `fix-issue` skill whose steps include running tests). This is documentation of practice, not evidence.
- Gloaguen shows that naming pytest or another tool in a context file makes agents use it "almost exclusively" and that agents run more tests with a file present; removing the testing section lowered cost without a significant accuracy change. So an always-loaded instruction demonstrably changes test-running behaviour, at the price of added steps and cost. There is no skills condition, so nothing shows a skill would do the same, better or worse.
- Vercel's 56% non-invocation of a skill suggests that a skill's benefit depends on being triggered, which for a general "run tests" instruction is a matter of description matching; the effect on tests specifically was not measured. This is an inference from an adjacent task, flagged as such.
- The plausible mechanisms for a skill (the standing file stays shorter; the body is loaded near the moment of use) are only the vendors' loading model, unmeasured for tests. The adherence decay within a session ([factorial study](sources/instruction-adherence-config-files-factorial.md)) is consistent with the idea that late-loaded text is better followed than start-of-session text, but that study did not test position in time or skills, so this is speculation.

Plainly: the guide's claim is the author's unmeasured experience, and the published material found neither supports nor refutes it; the vendor documents lean the other way in what they recommend.

## Hooks

Vendor claim, repeated in the [best practices](sources/claude-code-best-practices-claude-md.md) and [features](sources/claude-code-features-overview.md) pages: instructions are advisory and hooks are deterministic; a rule that must hold every time should be a hook; hooks cost no context unless they return output. No measurement was found of instruction versus hook compliance; the vendor statement follows from how hooks execute, not from a study. The testing-specific version is already in the testing notes.

## Not verified or not found

- Any experiment comparing AGENTS.md, skill and hook placement for getting tests run, or for any instruction type.
- Vercel figures and Lulla, Khatri and factorial-study details rest on summarised abstracts or blog text; the 34,000-skill and IFScale decay-pattern details partly on snippets.
- Whether the results hold beyond Python and benchmark-style tasks, or for current model versions.
- Copilot's page on skills, Copilot coding-agent best-practices, Anthropic's "Steering Claude Code" blog post, and "lost in the middle" style position studies were not read.
