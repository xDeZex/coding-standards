# What belongs in AGENTS.md, a skill or a hook: findings

Scope: evidence gaps only. How the files are read, sized and layered is already in [the conventions conclusion](../agents-md-conventions/conclusion.md) and its sources (for example [Claude Code memory](../agents-md-conventions/sources/claude-code-memory.md), [Codex](../agents-md-conventions/sources/codex-agents-md.md), [Claude Code skills](../agents-md-conventions/sources/claude-code-skills.md)); the testing loop and hook-as-gate material is in [the testing conclusion](../testing-feedback-loop/conclusion.md). This note adds what those did not cover. Most of the studies below are preprints. In a re-read pass on 2026-09-26 every source was opened as raw text (full paper PDFs through pdftotext, vendor and blog pages as raw HTML), and the source notes and this conclusion were corrected against them; each source note states how it was read. Several claims from the first version, which rested on summarised abstract pages, were wrong and are fixed below.

## Do context files help at all

The one substantial controlled study, [Gloaguen et al.](sources/gloaguen-evaluating-agents-md.md) (SWE-bench plus 138 real issues from 12 niche Python repos with committed files, four agents), finds that context files do not generally improve task success and raise cost by over 20% on average, and that agents do follow them. LLM-generated files: success down 0.5% (SWE-bench) and 2% (CtxBench), neither significant, cost up 20% and 23%. Developer-written files: success up 2.4% on average (p = 21%, not significant), cost up by at most 19%, and better than LLM-generated files by about 7% (p = 3.8%). Repository overviews did not help agents find the relevant files sooner. The authors say such files are useful for non-standard practices and should hold only what is not already in the README.

[Khatri](sources/khatri-context-files-two-agent-ablation.md) (single author, 17 tasks, 3 repos, Claude Code and Codex, 288 runs) also finds no measurable correctness effect from context delivery, bounded within about 10 to 15 points but with low power (it says about 120 to 200 tasks would be needed for 10 points). On efficiency the studies do not agree in an obvious way: [Lulla et al.](sources/lulla-agents-md-efficiency.md) report lower median runtime (-28.6%) and output tokens (-16.6%) with an AGENTS.md, but on one agent only (Codex, gpt-5.2-codex), on 10 repos and 124 small PRs whose files were selected for conventions, architecture or project description content, and their "comparable task completion" rests on a manual check of 50 outputs, not a correctness evaluation. Khatri found Codex efficiency flat across strategies. The reason for the differences between studies is not established; Khatri suggests the tasks on which context could matter differ by agent. All are Python or small-sample, and none is shown to be peer reviewed. [Agent READMEs](sources/agent-readmes-context-files-empirical.md) is descriptive only: testing instructions are the most common content of real files (75.9% of 2,303, by an automatic classifier).

## Short and non-inferable

The three vendors converge, always as assertion without data. Anthropic: include what Claude cannot infer from code, cut any line whose removal would not cause a mistake, and expect an over-long file to be partly ignored ([best practices](sources/claude-code-best-practices-claude-md.md)); under 200 lines ([features overview](sources/claude-code-features-overview.md)). OpenAI: short and accurate beats long and vague, and add to it after the same mistake twice ([Codex](sources/codex-best-practices.md)). GitHub: the length limit ("no longer than 2 pages", "not task specific") appears only inside a prompt the page supplies for asking the Copilot cloud agent to generate the file, not as a rule for hand-written files ([Copilot](sources/github-copilot-repository-instructions.md)). The "non-inferable" rule has empirical backing in Gloaguen (overviews and duplicated README content did not help; with the repository's other documentation removed, LLM-generated files improved success by 2.7% on average and beat developer-written ones), but that study did not test which individual human-written lines matter.

## Does length reduce adherence

Vendor claim: yes ([Anthropic](sources/claude-code-best-practices-claude-md.md)). Measured in real Claude Code sessions, a [factorial study](sources/instruction-adherence-config-files-factorial.md) (single author; 1,650 sessions, two TypeScript codebases, Sonnet 4.6 mainly) found no detectable effect of file size (25, 100, 250, 500 lines), instruction position (line 2 to line 250 of a 250-line file), file architecture or a contradicting instruction in an adjacent file. Only the size and conflict nulls have Bayesian support; the position and architecture nulls are failures to reject. The instruction tested was a single trivial one (emit a `// @tracked` annotation on generated functions; baseline compliance 60 to 68%), so it is not evidence about many realistic instructions. The same study found compliance falling by about 5.6% in odds per additional function generated within a session (OR 0.944), an effect it says was identified during analysis rather than pre-specified, is non-monotonic, varies by task and concentrates in the first three to four functions. Gloaguen also found no clear dependence of success or cost on context-file length. In the synthetic [IFScale](sources/ifscale-instruction-density.md) benchmark (keyword-inclusion rules in report writing, 10 to 500 instructions) adherence falls as instruction count rises, the best models reaching 68% at 500 but staying near-perfect up to about 150 instructions for the top reasoning models; the bias toward earlier instructions peaks at 150 to 200 instructions and fades beyond 300. So the evidence for "shorter is followed better" is vendor assertion plus a synthetic benchmark, and the one agentic test found no size effect for one trivial instruction at 25 to 500 lines.

## Skills versus always-loaded instructions

First-party guidance describes the mechanism consistently: skills load only name and description up front, the body when the agent judges it relevant, further files on demand ([Anthropic blog](sources/anthropic-agent-skills-engineering-blog.md), [authoring guide](sources/anthropic-skills-authoring-best-practices.md), [features overview](sources/claude-code-features-overview.md)). Its stated placement rule is: always-needed facts and "always do X" rules in CLAUDE.md; sometimes-needed reference material and repeatable or invocable workflows in a skill; anything that must happen every time in a hook. Skill selection depends on the description, and the docs warn of missed or wrong skills.

Measured evidence is thin and much of it is about whether the skill gets loaded. [Vercel](sources/vercel-agents-md-outperforms-skills.md) (vendor blog, one framework, one task type, no sample sizes, agent not named) found the skill was never invoked in 56% of eval cases by default (pass rate 53%, same as the 53% no-docs baseline; test pass rate 58% versus 63% baseline), 79% pass rate with an explicit instruction (itself added to AGENTS.md) that raised invocation to 95% or more, versus 100% for a compressed docs index in AGENTS.md. The authors also write that skills suit "vertical, action-specific workflows that users explicitly trigger". The [in-the-wild benchmark](sources/skills-in-the-wild-benchmark.md) measured skill loading directly: with curated skills available and the agent deciding, Claude Opus 4.6 loaded any skill in 62.2% of trajectories and all curated skills in 49% (pass rate 51.2% versus 55.4% when the skills were force-loaded), and gains shrank toward the no-skills baseline when skills had to be retrieved from a 34,198-skill pool. [SkillsBench](sources/skillsbench-benchmark.md) finds curated skills, supplied with the task, raise pass rate from 33.9% to 50.5%, with the smallest domain gains for software engineering (+11.6 points); focused bundles beat large ones (one skill +18.0, two to three +19.0, four or more +10.1); and it reports task-shipped skills were invoked 85 to 99% of the time on the configurations it lists, so invocation is not universally low. Self-generated skills scored below the no-skills baseline. None of Vercel and these benchmarks involves test-running instructions.

## The claim "test-running instructions are better in a skill than AGENTS.md"

No evidence found for it, and no measurement that compares the two for this purpose. What exists points elsewhere or is silent:

- Vendor wording on where test and build commands go, checked against the pages: Anthropic's best-practices page has "Testing instructions and preferred test runners" in its include table for CLAUDE.md and an example CLAUDE.md line "Prefer running single tests, and not the whole test suite, for performance" ([best practices](sources/claude-code-best-practices-claude-md.md)); the features page says "Use CLAUDE.md for instructions every session needs: build commands, test conventions, project architecture" and its example line is "Use pnpm, not npm. Run tests before committing" ([features](sources/claude-code-features-overview.md)). The same best-practices page also offers a Stop hook as "a deterministic gate" that "blocks the turn from ending until it passes" for a test check, and its `fix-issue` skill example (a manually invoked workflow) has "Write and run tests to verify the fix" as one step. [Codex](sources/codex-best-practices.md) lists "Build, test, and lint commands" and "What done means and how to verify work" as things a good AGENTS.md covers, says testing guidance "can come from either the prompt or AGENTS.md", and does not name skills for it. [Copilot](sources/github-copilot-repository-instructions.md) asks for test steps only inside a generator prompt for copilot-instructions.md; its page states no placement rule. So two vendors (Anthropic, OpenAI) state test commands belong in the always-loaded file, and the third does so only implicitly. This is documentation of practice, not evidence.
- Gloaguen shows that tools named in a context file ("uv, pytest, or repository-specific tools") are "used almost exclusively if they are mentioned" and that agents run more tests with a file present; in a one-model ablation (GPT-5.2), removing the testing section from LLM-generated files lowered cost significantly (CtxBench $0.47 to $0.37) without a significant accuracy change. So an always-loaded instruction demonstrably changes test-running behaviour, at the price of added steps and cost. There is no skills condition, so nothing shows a skill would do the same, better or worse.
- The closest measurement found is in Khatri: an exploratory, post hoc analysis on one repository (opshin) whose AGENTS.md warns that the full test suite takes over 20 minutes. Claude's full-suite pytest runs per cell were 3.67 with no context, 2.44 with the file always injected and 1.67 with the same content available as a file to read on demand (4 tasks, p = 0.25; time 2,689 s, 2,066 s, 2,032 s, p = 0.125). That compares always-loaded with on-demand delivery of a test-running warning and points, weakly, the other way from "always-loaded is better", but it is not a skill (a wiki file read with the Read tool), one agent, one repository, and not significant; Codex and the other repository showed no such effect.
- Vercel's 56% non-invocation and the in-the-wild benchmark's 62% any-skill loading suggest that a skill's benefit depends on being triggered, which for a general "run tests" instruction is a matter of description matching; the effect on tests specifically was not measured. This is an inference from adjacent tasks, flagged as such.
- The plausible mechanisms for a skill (the standing file stays shorter; the body is loaded near the moment of use) are only the vendors' loading model, unmeasured for tests. The adherence decay within a session ([factorial study](sources/instruction-adherence-config-files-factorial.md)) is consistent with the idea that late-loaded text is better followed than start-of-session text, but that study did not test position in time or skills, so this is speculation.

Plainly: no paper found compares test-running instructions in a skill against AGENTS.md. The nearest evidence is Khatri's exploratory always-on versus on-demand comparison for one test-suite warning (directional, not significant, not a skill). The vendor documents lean towards the always-loaded file for test and build commands.

## Hooks

Vendor claim, repeated in the [best practices](sources/claude-code-best-practices-claude-md.md) and [features](sources/claude-code-features-overview.md) pages: "Use hooks for actions that must happen every time with zero exceptions"; "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens"; "If a rule must hold every time, make it a hook rather than a prompt instruction"; hooks cost "Zero unless the hook returns output". The features page frames skills as for reference material, "knowledge rather than a script" and invocable workflows, not only reference material. No measurement was found of instruction versus hook compliance; the vendor statement follows from how hooks execute, not from a study. The testing-specific version is already in the testing notes.

## Not verified or not found

- Any experiment comparing AGENTS.md, skill and hook placement for getting tests run, or for any instruction type. The nearest is Khatri's exploratory on-demand-file result described above.
- Whether the results hold beyond Python (Gloaguen, Khatri, Lulla) or TypeScript with one trivial instruction (factorial study), or for current model versions. Vercel's agent and model are not named; its sample sizes are not given.
- Whether Lulla's efficiency result holds for Claude Code (only Codex was run) or for task success (only a 50-output manual check).
- The two Claude-relevant instruction-adherence conclusions (no size effect; decay per generated function) rest on one single-author preprint each: the factorial study and, for on-demand delivery, Khatri.
- Copilot's page on skills, Copilot coding-agent best-practices, Anthropic's "Steering Claude Code" blog post, and "lost in the middle" style position studies were not read. The Anthropic engineering blog post on skills was read and says nothing on where test commands go.
