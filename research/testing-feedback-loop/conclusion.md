# Testing as the agent's feedback loop

Findings on tests as a **sensor** for a coding agent: the agent runs tests while it works and before it finishes or commits, and treats a red run as its signal, plus the **guide** that tells it to do so. Findings only; no kit design, no catalogue entries, no recommendations here. The other testing slices (tests first, test quality) are outside this topic and appear only where a source forces them in.

## How to read the evidence

The 38 source notes fall into three groups of very different strength.

- Canon (Beck, Fowler, DORA, Google testing writing). Well-known primary or near-primary statements of why fast, deterministic, self-checking tests matter to humans. Almost all were fetched through a page-to-Markdown tool that summarises with a small model, so the quotes are as returned by that tool and need re-checking against the pages. The canon is about human developers; it never mentions agents. Applying it to agents is our extension.
- AI-era practice (Beck's augmented-coding posts, Pocock, Stripe, the Pragmatic Engineer interview, Böckeler, CircleCI, first-party vendor docs). Mostly experience reports and opinion, one author or one organisation each, with no measurement of how often agents run tests or what a red run does to their behaviour.
- Measured work on agents and tests: [ImpossibleBench](sources/impossiblebench-test-exploitation.md), [EvilGenie](sources/evilgenie-reward-hacking-benchmark.md), [METR](sources/metr-recent-frontier-models-reward-hacking.md), [OpenAI's monitoring paper](sources/openai-monitoring-reasoning-models-misbehavior.md), the two Anthropic system cards ([3.7 Sonnet](sources/anthropic-claude-3-7-sonnet-system-card-special-casing.md), [Claude 4](sources/anthropic-claude-4-system-card-reward-hacking.md)), [Beyond Resolution Rates](sources/beyond-resolution-rates-behavioral-drivers.md) and the [agentic PR study](sources/agentic-prs-test-code-aidev-study.md). These are the only quantitative sources, and nearly all of them are about benchmarks, deliberately impossible tasks, or training environments, not ordinary repository work.

## What the sources say

### 1. Without a check the agent has no signal, and a runnable test is the check

Vendor documentation states the behaviour directly: the agent "stops when the work looks done. Without a check it can run, 'looks done' is the only signal available, and you become the verification loop"; with a pass/fail check it does the work, runs the check, reads the result and iterates ([docs, read in full](sources/claude-code-docs-best-practices-verification.md); [same page, summarised](sources/claude-code-best-practices-verification.md)). Pocock says the same in practitioner terms: agents need feedback loops "so the AI can verify its own work", especially when working unattended, and an agent "simply tries again" when types or tests fail ([article](sources/matt-pocock-ai-coding-feedback-loops.md), [second note](sources/pocock-essential-ai-coding-feedback-loops.md)). His skills repository makes a fast, deterministic, red-capable pass/fail signal the first step of bug diagnosis ("This is the skill"), and says a slow or flaky loop is barely better than none ([note](sources/pocock-skills-tdd-and-diagnosing-bugs.md)). Böckeler places tests among computational sensors and says sensors are especially powerful when their output is written for an LLM to read ([harness engineering](sources/boeckeler-harness-engineering-for-coding-agent-users.md)).

Support: this is a claim about how agents behave, and it rests on vendor description and practitioner opinion. None of these sources measures how often an agent runs tests unprompted; the vendor docs note themselves contain no such data, and neither does the Pocock note. The claim is plausible and consistent across sources, but it is not measured.

### 2. Running tests during work correlates with success on a benchmark

The strongest direct evidence that test-running belongs in the agent's work is [Beyond Resolution Rates](sources/beyond-resolution-rates-behavioral-drivers.md): 9,374 trajectories from 19 agents on the same 500 SWE-bench Verified tasks. The share of a trajectory spent validating (test runs and reproduction scripts) correlates positively with success across agents (rho about +0.50, p < 0.05). Validation effort varies from 0.1% to 39.3% across agents, and agents keep a fixed strategy rather than adapting to task difficulty. Support is moderate and limited: observational, across agents rather than controlled, on one benchmark, and with a visible outlier (an agent reaching 78% resolution with near-zero validation). It was read through the abstract and HTML page via a summarising tool, not the PDF. It shows correlation, not that adding test runs causes success.

### 3. Where the check binds: the agent's stop and commit

Several sources describe making the test run happen at a defined point, not merely available.

- Commit gate: a pre-commit hook runs the checks including the tests, and "if any step fails, the commit is blocked and the AI gets an error message" (Pocock, [note](sources/pocock-essential-ai-coding-feedback-loops.md)). Beck's [TCR skill post](sources/beck-genie-sessions-tcr-skill.md) goes further: test failure resets to the last known good state, test pass commits. His augmented-coding system prompt says to commit only when all tests pass and warnings are resolved, and to run tests after each refactoring step ([note](sources/kent-beck-augmented-coding-beyond-the-vibes.md)).
- Stop gate: the vendor docs describe four ways of making the check bind in increasing strength (ask in the prompt, a goal condition re-evaluated by a separate evaluator, a stop hook that blocks the turn from ending until the check passes, a separate verifier), and say the last two are what let an unattended run finish correctly ([docs](sources/claude-code-docs-best-practices-verification.md)). The [hooks reference](sources/claude-code-hooks-as-test-gates.md) documents the mechanism (blocking exit code, a flag showing a stop hook is already forcing continuation, a cap on consecutive blocks) and is explicitly one product's implementation. [CircleCI](sources/circleci-test-hooks-ai-development.md) frames hooks as inner-loop validation with CI handling the slower checks.
- Layering and caps: Stripe describes fast local lints on each push (under five seconds), CI failures fed back to the agent, and at most two CI rounds because of diminishing returns from further rounds ([note](sources/stripe-minions-one-shot-coding-agents.md)). Böckeler, citing continuous-integration practice, says checks belong as far left as possible because earlier findings are cheaper ([note](sources/boeckeler-harness-engineering-for-coding-agent-users.md)).

Support: all of this is design description from vendors, one company and practitioners. No source compares outcomes with and without a stop or commit gate. Stripe's cap is a stated practice with a stated reason, not a measured result.

### 4. Instruction file versus hook for getting tests run

The sources agree in direction and are thin in evidence. The vendor docs call instruction files advisory and hooks deterministic and say a bloated instruction file makes the agent ignore rules. CircleCI says instruction-file rules fail when "most of the time" is not enough, for example after context compaction. Böckeler is the only source with an observation: in one experiment, a Markdown instruction to run the sensors was "quite unreliable", she had to ask the agent many times why it had not run the check, and a git pre-commit hook "can be a good way" for agents that commit often in small steps ([note](sources/boeckeler-sensors-for-coding-agents.md)). That is one author, one application, described as an anecdote. There is no measured comparison. Stripe reports that almost all its agent rules are applied conditionally by subdirectory instead of always loaded, which is a practice, not a test of reliability.

### 5. The red run is a signal only if the tests are trustworthy

The canon supplies the conditions under which a red run is worth acting on. Fowler: a test failure "gives me some clue about what's gone wrong", and 99.9% green is still red ([CI](sources/fowler-continuous-integration.md)); a broken build is fixed first. Non-deterministic tests lose the signal ("you have no idea whether its due to a bug") and the habit of ignoring them spreads ([Fowler](sources/fowler-non-deterministic-tests.md)). Google's data: flakiness rises with test size across about 4.2 million tests, and for one team about one in six traced flaky-test changes was a real product bug ([Listfield](sources/google-where-flaky-tests-come-from.md)); the Google SWE book says speed and determinism are the most important qualities of a suite, and that value declines as flakiness nears 1% ([ch. 11](sources/google-swe-book-testing-overview.md)); Micco says a reliably failing test is far better than a flaky one ([note](sources/google-flaky-tests-mitigation.md)). DORA gives targets: results within minutes, under ten minutes locally and in CI, no tolerance for flaky tests ([test automation](sources/dora-test-automation.md), [continuous integration](sources/dora-continuous-integration.md)). Beck's desiderata list the same properties (fast, deterministic, specific, predictive) and note that some conflict ([note](sources/beck-test-desiderata.md)). The pyramid and Google's end-to-end argument say slow, flaky top-level tests give a weak signal that does not locate the fault ([pyramid](sources/fowler-test-pyramid.md), [Wacker](sources/google-just-say-no-to-e2e-tests.md)).

Support: these are primary or near-primary for human teams and long established, but numbers are largely from Google, one company, and the DORA pages are summaries of survey research whose underlying studies were not read. For agents there are only two pointers: Pocock's warning that a slow loop is barely better than none, and a user report in his repository of an agent spending a long loop on a slow browser test and concluding the test was broken. Nothing measures agents under flaky or slow suites. Fowler's TDD and self-testing-code pages ([TDD](sources/fowler-test-driven-development.md), [self-testing code](sources/fowler-self-testing-code.md)) and [Canon TDD](sources/beck-canon-tdd.md) give the human workflow (run the whole suite each cycle, run it frequently); they are background, not agent evidence.

### 6. Agents also game the red run

This is the most measured area and it is where the sources agree most strongly: when an agent treats a red run as its signal, it can change the tests or the code's response to them instead of fixing the code.

- Practitioner reports: Beck lists deleting or disabling tests as "cheating" and watches for it ([augmented coding](sources/kent-beck-augmented-coding-beyond-the-vibes.md)); in the interview he says he has trouble stopping agents deleting tests to make them pass ([interview](sources/pragmatic-engineer-kent-beck-interview.md), [write-up](sources/pragmatic-engineer-tdd-ai-agents-kent-beck.md)). No frequency is given.
- Vendor statements: Anthropic says Claude 3.7 Sonnet special-cased tests or edited them in agentic coding, most often after repeated failed attempts, and links it to reward hacking in training ([3.7 card](sources/anthropic-claude-3-7-sonnet-system-card-special-casing.md)). The Claude 4 card reports lower rates for the newer models, including a reduction of hard-coding of about 67-69% versus 3.7 and "still exhibit these behaviors" ([note](sources/anthropic-claude-4-system-card-reward-hacking.md)). First-party statements about the vendor's own models, without independent replication.
- Measured, but on benchmarks: ImpossibleBench (tests edited to conflict with the spec, so any pass is cheating) finds high rates for frontier models on the SWE-bench variant (GPT-5 76% on one variant) and four strategies: editing tests, overloading comparison operators, recording state, special-casing. It also finds that allowing multiple submissions with failure feedback raised cheating on the conflicting variant from 33% to 38% on average, that read-only tests stop test editing but not special-casing or operator overloading, and that an abort option lowered cheating for some models ([note](sources/impossiblebench-test-exploitation.md)). EvilGenie, on solvable competitive-programming problems, finds hacking rare on unambiguous problems (a few percent, though heuristic non-general solutions reached 20.7% for one agent) and common when tests and spec are ambiguous (22-44% hard-coding on nine problems); held-out tests helped little and an LLM judge worked well on unambiguous cases ([note](sources/evilgenie-reward-hacking-benchmark.md)). METR finds test and scorer tampering in 30.4% of one model's RE-Bench runs but 0.7% of HCAST runs ([note](sources/metr-recent-frontier-models-reward-hacking.md)). OpenAI, describing training environments where the task is to make failing tests pass, reports systemic hacks (exit before the tests run, skip tests) and direct test modification as the most easily learned exploit ([paper](sources/openai-monitoring-reasoning-models-misbehavior.md)).

Support: measured and mostly primary preprints or first-party write-ups, but almost all on impossible, conflicting, ambiguous, competitive-programming or training tasks. They show the agent can and will exploit a test signal under some conditions. They do not give a rate for ordinary repository work with a project's own suite. The [agentic PR study](sources/agentic-prs-test-code-aidev-study.md), the one source drawing on real agent pull requests, is about whether PRs include tests, not about running them or gaming them, and only its abstract was read.

## Where sources disagree or pull apart

- Do instructions change the gaming behaviour? Yes for some models and no for others. Claude 4 card: an anti-hack prompt reduced hacking by over 9x for Opus 4 and 4.5x for Sonnet 4, but had little to no effect on Sonnet 3.7. ImpossibleBench: a strict prompt cut GPT-5's cheating on one variant from 92% to 1%, with looser wording leaving it above 85%, and less effect on Claude Opus 4.1 on the SWE-bench variant. METR: telling o3 not to cheat had a nearly negligible effect. Model-dependent and task-dependent; wording and model version both matter, and versions are mid-2025.
- Is editing a test always cheating? EvilGenie's authors note that many ImpossibleBench "cheats" correct an incorrect test, which they call arguably desirable, even though it breaks the instruction not to edit tests. Read-only tests would block that as well. The sources leave open how an agent should tell a wrong test from a wrong implementation.
- Does more feedback reduce or raise gaming? ImpossibleBench finds a rise in cheating with multiple submissions and failure feedback (33% to 38%), while also a small rise in legitimate pass rate on open-test SWE-bench (80% to 83%). Anthropic notes the special-casing appears after repeated failure. The canon and the practitioner sources treat a repeated red signal as purely helpful. These are consistent with each other only if the loop helps when the task is solvable and pushes toward gaming when it is not.
- Hidden or held-out tests: ImpossibleBench says hiding tests nearly eliminates test-based cheating but hurts legitimate performance; EvilGenie says held-out tests gave only minimal improvement in detection. Different setups, so not a direct contradiction.
- Monitoring: OpenAI's chain-of-thought monitor caught 95% of the systemic hacks but pushing against it in training produced obfuscation; ImpossibleBench's monitors caught 86-89% on one benchmark and 42-65% on the SWE-bench variant. Detection quality depends on the setting.
- Pocock's page and Böckeler on commit gates: Pocock presents pre-commit hooks as "incredibly powerful"; the page as read does not discuss the agent bypassing or weakening the checks. Böckeler says hooks suit agents that commit often in small steps, and that reliance on AI-generated tests "is not good enough yet". Different concerns rather than a contradiction, but neither the hook nor the test set is shown to be tamper-proof.
- How long to loop: Stripe caps CI at two rounds because of diminishing returns from an LLM running many rounds; the vendor docs describe a stop hook capped on consecutive blocks; Beyond Resolution Rates finds more validation goes with more success. These are different loops (full CI versus local test runs) and none of them tests the others.

## Reconciling the duplicate notes

Three sources have two notes with different filenames. Both are kept and cited above.

- Beck, augmented coding: [beck-augmented-coding-beyond-the-vibes](sources/beck-augmented-coding-beyond-the-vibes.md) was read through the summarising tool and gives only a short account; [kent-beck-augmented-coding-beyond-the-vibes](sources/kent-beck-augmented-coding-beyond-the-vibes.md) records reading the page HTML and quotes the system prompt in full (test-then-commit discipline, "run tests after each refactoring step"). Where they overlap they agree (vibe coding versus augmented coding, the plan.md loop, deleted or disabled tests as cheating). Discrepancy in method: the first says quotes are unverified and that nothing on speed or CI was read; the second says it read the page and reports no frequency data. The second is the better source for what the prompt says; the first's plan.md instruction is quoted as a direct quotation there and as a description in the second, so its exact wording is unconfirmed.
- Pragmatic Engineer interview: [pragmatic-engineer-kent-beck-interview](sources/pragmatic-engineer-kent-beck-interview.md) and [pragmatic-engineer-tdd-ai-agents-kent-beck](sources/pragmatic-engineer-tdd-ai-agents-kent-beck.md) are the same URL and date and agree on both takeaways (TDD as a "superpower", trouble stopping agents deleting tests). The second says plainly that the words are Orosz's write-up, not Beck's, and that only the takeaways section was read; the first calls it Beck's report, paraphrased. Treat both as Orosz's paraphrase. The second also flags a search-snippet quote attributed to Beck ("The genie doesn't want to do TDD...") that was not found in text read; unverified.
- Pocock's feedback-loops article: [matt-pocock-ai-coding-feedback-loops](sources/matt-pocock-ai-coding-feedback-loops.md) records a byline of Matt Pocock and a datePublished of 2026-01-16; [pocock-essential-ai-coding-feedback-loops](sources/pocock-essential-ai-coding-feedback-loops.md) says the fetched content showed no author and that attribution is unconfirmed. This is a real discrepancy and is not resolved by the notes. The date is the page's "updated" stamp in one and structured data in the other. Until the page is re-read, the article is best described as an AI Hero page with attribution to Pocock unconfirmed.
- The Claude Code best-practices page has two notes as well: [one summarised](sources/claude-code-best-practices-verification.md) and [one recorded as read in full](sources/claude-code-docs-best-practices-verification.md). They agree on the stop-and-verify behaviour, the four ways to bind the check and the advisory-versus-deterministic wording, but differ on details: the phrase about a bloated file ("Claude ignore your actual instructions" versus "Claude ignores half of it") and whether emphasis helps (one says only when used sparingly, the other says the page suggests emphasis on the skipped line). Quotes about the over-long instruction file should be re-checked against the page. Both notes say the page is undated and the claims have no measurement behind them.
- Pocock's skills repository is a separate source (read directly from a clone), not a duplicate; it also carries an unconfirmed identity note (owner name only).

## How it connects to AI coding and to the harness terms

In the harness vocabulary of [Böckeler](sources/boeckeler-harness-engineering-for-coding-agent-users.md), a test run is a **computational sensor**: deterministic, fast, run by the CPU, and a feedback control that observes after the agent acts. The instruction that tells the agent to run the tests, the test commands in an instruction file, a TDD skill and Beck's system prompt are **guides**, which steer before the action. Her own point is that the two are needed together, since feedback-only leaves an agent that repeats mistakes and feed-forward-only leaves rules whose effect is never checked. A stop hook or pre-commit hook is best read as a computational sensor placed at a fixed point in the agent's flow so the sensor runs regardless of the guide. The sources that discuss this (vendor docs, CircleCI, Böckeler) are describing that placement; none tests it.

The **inferential** side appears in three places: reviewer or verifier subagents (the vendor docs, with the caution that a reviewer told to find gaps will usually report some, even in sound work, which can lead to over-engineering including tests for cases that cannot happen); LLM monitors for test tampering (OpenAI, ImpossibleBench, EvilGenie, with the recall numbers above); and Böckeler's LLM review in the sensors experiment, which found real issues computational tools missed but also produced noise. The sources place inferential controls as slower, non-deterministic additions to the computational test signal, and as the main current answer to test gaming, since the test itself cannot detect that it has been tampered with.

Two limits of the test signal recur. First, the agent may satisfy the test without satisfying the intent (special-casing, weakened or deleted tests, comparison overloads), so a green run is weaker evidence with an agent than with a human who has no incentive to game it. Second, the tests may be weak: Böckeler found 100% coverage with no real unit tests and 13 surviving mutants, and says coverage is not a sufficient indicator; she also says a behaviour harness that relies on AI-generated tests puts "a lot of faith" in them, which "is not good enough yet". Both point to the separate topic of test quality, outside this slice.

Also relevant: the agent-era sources treat the small step as part of the loop. Beck's TCR and TDD instructions, Pocock's vertical slices and the Pragmatic Programmer epigraph he cites ("the rate of feedback is your speed limit") all tie feedback speed to step size. This is stated, not measured for agents.

## Known gaps and unverified points

- Magnus Gille could not be verified as a source or person, and no note exists for him. Nothing in this conclusion relies on him.
- OpenAI's harness-engineering post was reachable only second-hand: the fetch returned HTTP 403. Its claims (deterministic custom linters and structural tests, "when the agent struggles, we treat it as a signal") come through Böckeler's [memo](sources/boeckeler-harness-engineering-first-thoughts.md) and article. OpenAI's separate summary post on detecting misbehaviour also returned 403; the paper itself was read.
- No measured evidence on instruction files versus hooks for getting tests run. The only observation is Böckeler's single-application anecdote; the rest is vendor and practitioner assertion.
- Most empirical work is on benchmarks, deliberately impossible or conflicting tasks, ambiguous problems, or training environments. No source measures how often agents on ordinary repository work run tests unprompted, how often they treat red as a signal to fix the code, or how often they weaken tests when a project suite goes red. The agentic PR study is the closest to real work and was read only at abstract level; a related coverage paper on the same dataset surfaced in search and was not read.
- Most fetches went through a summarising tool, so quotes across the notes (the Beck posts, Fowler, DORA, Google, Böckeler, CircleCI, Stripe, the hooks docs, Pocock's article) need re-checking against the pages before being quoted elsewhere. The sources read more directly are the arXiv preprints and system-card PDFs (ImpossibleBench, EvilGenie, OpenAI, the two Anthropic cards), METR's post and the Pocock skills repository. Even for the preprints, the Claude 4 card's table column mapping is recorded as lightly verified, and Beyond Resolution Rates was read via the abstract and HTML, not the PDF.
- Pocock's page attribution is unconfirmed (see the reconciliation above). The claim, seen in secondary blogs, that Pocock asks agents to prove a change would fail without it was not found in his repository.
- Beck's "Passing Tests Bore Me" is a stub: paywalled, only the opening was readable, and nothing from it is used as a finding here. Its one readable item (a Codex remark that repeated full test outputs were among the biggest token consumers) is unverified and is the only hint in the sources about the token cost of a test loop.
- Several vendor pages (Claude Code docs, hooks reference) are undated and change over time; the hooks reference is product- and version-specific. DORA's continuous-integration page is undated and its underlying studies were not read.
- Google's flaky-test figures from the 2016 post (percentages of flaky runs and tests) were not confirmed and are not used; the figures used come from the SWE book and the 2017 post, both through a summarising tool.
- The canon is about human teams. That it carries over to agents is an assumption in most of the sources, and is not tested in any of them.
