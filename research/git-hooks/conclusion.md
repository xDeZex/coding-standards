# Git hooks

Findings on what git hooks are good and bad at across the uses people make of them, and what someone weighs when deciding whether a git hook is the right control for an AI coding agent's failure. Collected to feed a general handbook on git hooks as a control. Findings only; no kit design, no catalogue entries, no recommendations. A git hook is a script git runs at a git event; it is not an agent hook, which the coding-agent harness runs at a point in the agent's flow (see [CONTEXT.md](../../CONTEXT.md)). The agent-hook side is in [hooks in coding-agent harnesses](../agent-hooks/conclusion.md), and the narrower [hooks as a test gate](../hooks-as-test-gate/conclusion.md) already covers the commit gate, `--no-verify`, the per-clone problem and the CI-backstop argument. This conclusion adds to those and links to their notes rather than repeating them.

The conclusion has two parts, kept apart so evidence is not read as confirming an opinion or the reverse: what practitioners and experts do and recommend, then what the evidence shows.

## What practitioners and experts do and recommend

Twelve notes in [sources/](sources/) record what named people or organisations say or do about git hooks and agents. Each was written from the raw page (curl and html-to-text), a raw repository file or raw tweet JSON, not through WebFetch, and each says how. All are opinion or first-party practice; none gives data. Trust varies and the notes say so. Descriptions below come from the notes; where a note says its description of the speaker is the writer's background knowledge and not read from the page, it is marked "(unverified)".

### Who says what

- Matt Pocock (TypeScript educator behind Total TypeScript and AI Hero, and author of a widely used public set of agent skills). His feedback-loops article calls a Husky pre-commit hook that runs lint-staged, the type check and the full test suite "incredibly powerful" for agent work: "If any step fails, the commit is blocked and the AI gets an error message", and "AI agents don't get frustrated by repetition ... the agent simply tries again" ([article](sources/pocock-feedback-loops-husky-pre-commit.md)). His Ralph-loop tips say "The best setup blocks commits unless everything passes. Ralph can't declare victory if the tests are red", and also give the agent a prompt instruction to run all checks before committing, without saying which is more reliable ([tips](sources/pocock-ralph-tips-pre-commit-hooks-block-commits.md)). His skills repository is a different signal (see the disagreements below): the `setup-pre-commit` skill lives in `skills/misc/`, described as "Tools I keep around but rarely use", and his guard against dangerous git commands (`git push`, `git reset --hard`, `git clean -f` and others) is a Claude Code agent hook, not a git hook. His in-progress retro skill names "a custom rule in the repo's own linter, a new pre-commit hook, or a new CI job" as interchangeable homes for a deterministic check, and says judgement calls go in a standards file ([note](sources/pocock-skills-repo-setup-pre-commit-in-misc.md)). Neither article discusses `--no-verify`, hook runtime or per-clone install.
- Birgitta Böckeler (Distinguished Engineer and AI-assisted delivery expert at Thoughtworks, per her own page; her harness-engineering article supplies this repo's vocabulary of guides, sensors and controls). In an experiment on one app she found that telling the agent in AGENTS.md or a skill to run her sensors was "quite unreliable" ("I had to ask the agents many, many times why it had not run the sensors check"). She lists a git hook as one of four ways to force the check: "For users who like their agents to do frequent small commits, a pre-commit hook can be a good way to force a sensors check to take place before code even gets into a commit". She did not try it as far as the page says; the only git hook she reports running is Gitleaks, which she counts as a sensor because it "will give the agent feedback when it tries to commit" ([sensors article](sources/bockeler-sensors-git-hook-as-integration-option.md)). Her harness article lists "a pre-commit (or coding agent) hook running ArchUnit tests" as alternatives without ranking them, puts fast checks (linters, fast test suites, a basic review agent) before the commit and expensive ones in the pipeline, repeats the fast ones there, and says LLM checks are "expensively and probabilistically. Not on every commit" ([note](sources/bockeler-harness-engineering-hook-placement-and-timing.md)). Neither page discusses `--no-verify`, hook speed or per-clone install.
- Stripe engineering (Stripe's account of its internal "minions" coding agents, which the post says merge over a thousand PRs a week; a company statement, not measured data). Stripe describes "shifting feedback left" and pre-push hooks that fix common lint issues, fed by a background daemon so fixes arrive "well under a second on a push". For the agent, lint is a deterministic node in Stripe's own orchestration ("blueprint") that loops locally before the branch is pushed, followed by one iteration against the full CI suite and one retry, then a human: "It's infeasible to run all tests locally", and CI runs "cost tokens, compute, and time". The tests run in CI, not in a hook. The note does not say whether an agent's `git push` goes through the same pre-push hook, or how often the hook catches anything ([note](sources/stripe-minions-part-2-pre-push-hooks-and-ci-rounds.md)).
- Addy Osmani (author of widely read engineering posts, including the harness-engineering article used here; his affiliation is stated differently in two notes: this topic's note says the page describes him as a Member of Technical Staff at Anthropic working on Claude Code after 14 years at Google, while a note in [agent-hooks](../agent-hooks/sources/addy-osmani-agent-harness-engineering-hooks.md) describes him as a Google Chrome engineering leader, so it is unresolved here). His "ratchet": after an agent merged a commented-out test, he adds an AGENTS.md rule, then makes "the next version of my pre-commit hook" grep the diff for `.skip(` and `xit(`, then makes his reviewer subagent flag it, so one failure gets an instruction, a git hook and a review agent together. "Hooks are what separate 'I told the agent to do X' from 'the system enforces X.'" He lists "before commit" as one lifecycle point beside agent events and draws no line between git hooks and agent hooks. Constraints are added only after a real failure and removed when a capable model makes them redundant ([note](sources/osmani-agent-harness-engineering-pre-commit-ratchet.md)).
- Geoffrey Huntley (creator of the Ralph Wiggum loop technique for autonomous agents (unverified); the page says he is joining Antithesis, a deterministic-testing company). One line found: Antithesis together with "adversarial code reviews by an LLM and with language analyzers driven by pre-commit hooks" will let people and agents "deliver reliable software". The hook is one of three layers. Secondary summaries say he uses pre-commit hooks, property tests and snapshot tests; that was not found on any page read ([note](sources/huntley-engineer-away-the-slop-pre-commit-analyzers.md)).
- Jesse Vincent (author of the Superpowers skills and workflow plugin for coding agents (unverified)). His own instruction file says "Be vigilant to make sure nobody ever skips, evades or disables a pre-commit hook", so he assumes hooks exist and uses an instruction, not a block, against bypass; no reason or incident is given. A draft Superpowers worktree spec adds a step to symlink the main repo's hooks into a new worktree because worktrees "do not inherit the parent repo's hooks directory", which "prevents pre-commit checks, linters, and other hooks from silently stopping when work moves to a worktree". That is a draft-spec statement, not shipped behaviour, and his claim about what git does was not checked ([note](sources/vincent-obra-claude-md-never-skip-pre-commit.md)).
- Peter Steinberger (founder of PSPDFKit (unverified); says agents write "pretty much 100%" of his code on a roughly 300k-line TypeScript app). On agent hooks: "models are incredibly clever and no hook will stop them if they are determined". On git hooks, in passing: "If you don't know or don't use ast-grep as codebase linter, stop here and ask your model to set this up as a git hook to block commits." He works without worktrees or PRs with several agents in one folder, and his `/commit` instructions tell each agent to commit only its own changes so that an agent does not "freak out about other changes and tries to revert things if linter fails". He does not describe a hook of his own, its speed or `--no-verify` ([note](sources/steinberger-just-talk-to-it-hooks-and-git-hook-linter.md)).
- Steve Kinney (developer educator who teaches courses on front-end and AI-assisted engineering (unverified); the page is a lesson in his workshop). Weaker trust than the above: a teaching account with concrete rules, not a long record. Speed rule: "pre-commit takes under ten seconds, pre-push takes under two minutes. Anything slower belongs in CI", with typecheck, knip and unit tests in pre-push. Secret scanning is "the one I care about most". "If the team starts reaching for `--no-verify` regularly, the hook is too strict. Tune it." For agents he writes "Never use `--no-verify`" as an instruction, then says "if you want an actual enforcement boundary, use the agent's hook or permissions system", and gives a Claude Code PreToolUse hook and a Cursor `beforeShellExecution` hook that deny `--no-verify`. He layers an instruction, an agent hook guarding the git hook, and the git hook. He prefers Lefthook to Husky for new projects, partly because "you can point the agent rules at a single file", and says logic in pre-rebase is "probably solving a process problem with a technical tool". No measured effect ([note](sources/kinney-lefthook-self-testing-agents-no-verify.md)).
- Ryan Carson (founder of Treehouse and a public builder using Amp and Claude Code (unverified)). Weakest trust: an enthusiast's tweet. He says a Husky pre-commit hook can run the agent non-interactively, for example `amp -x "Oracle, review changes we're about to commit"` (`-p` in Claude Code), as an "automatic quality gate" beside tests and linting. That is a model call on every commit. No result, cost, latency or failure is claimed ([note](sources/carson-tweet-pre-commit-hook-runs-agent-review.md)).
- No git-hook statement was found from Kent Beck, Simon Willison, Boris Cherny, Armin Ronacher or Steve Yegge. None of the twelve notes describes them, so they are not described here; their absence is not evidence about their views.

### Where they agree

Most of the nine above who name a git hook use or recommend it as a place to run deterministic checks so the agent gets failure output before or at the commit: tests, types, lint, secrets, a grep for skipped tests, a structural linter. Nobody in these notes says a git hook is enough alone: Böckeler and Stripe repeat or move checks into CI, Kinney sends anything slow to CI, Pocock names CI as an alternative home, Osmani adds an instruction and a review agent, Vincent and Kinney add an instruction against bypass.

### Where they disagree or differ

- Hooks as the enforcement layer versus their limits. Osmani says hooks are what make "the system enforces X" true; Pocock says a commit gate means Ralph "can't declare victory if the tests are red". Steinberger says "no hook will stop them if they are determined" (he says this of Claude Code agent hooks, not git hooks). Kinney says a git hook is not an enforcement boundary against an agent that can pass `--no-verify`, and puts the boundary in the agent's hook or permissions. Vincent handles bypass with an instruction, Kinney with an instruction plus an agent hook. Böckeler recommends it only for users whose agents commit often in small steps. So the sources place the git hook as the feedback layer and split on what actually enforces it.
- Model calls at commit time. Carson runs an agent review inside pre-commit on every commit. Böckeler says LLM checks are expensive and probabilistic, "Not on every commit", while listing a "basic code review agent" among things fast enough to run before a commit; Osmani puts review in a reviewer subagent, not the hook; Huntley puts LLM review as a separate layer beside pre-commit analyzers. Carson gives no cost or result, Böckeler no measurement.
- Full test suite on commit. Pocock's hook runs the type check and full tests on every commit (his skill notes lint-staged is fast and staged-only, "then full typecheck and tests"). Kinney puts pre-commit under ten seconds and tests in pre-push or CI; Böckeler puts fast test suites before commit and expensive checks in the pipeline; Stripe says all tests cannot run locally and runs them in CI. Pocock does say elsewhere that the rate of feedback is "your speed limit"; his articles give no runtime limit.
- How much Pocock relies on the git hook. His articles call it "incredibly powerful" and "the best setup"; his skills repo files the setup skill under tools he rarely uses, and for dangerous git commands he uses an agent hook. The notes do not say why he classes it as rarely used or whether his daily practice changed; do not read the two as a contradiction, but they are not the same strength of endorsement.
- Where the checks run. Stripe's pre-push hooks serve human developers; for its agents the lint check is a step in its own orchestration and tests run in CI. Böckeler cites Stripe's pre-push hooks as an example of shifting feedback left; Stripe's own post, as read, does not say the agent's push runs through them. Böckeler's own sensors run in the agent's session through a CLI, and only Gitleaks runs in a git hook. Osmani and Böckeler show a git hook and an agent hook as alternative places for the same check; Kinney and Pocock use each for a different job (agent hook for policing commands, git hook for quality gates).
- Instruction versus hook. Böckeler finds an instruction to run checks "quite unreliable"; Pocock's Ralph tips use both an instruction and the hook; Vincent's protection against skipping is an instruction alone.

### Practitioner claims with no evidence behind them

The evidence in the second part does not test any of these. Where the second part has related single reports, they are noted there.

- Pocock: that a pre-commit hook is "incredibly powerful" for agents, and that an agent "simply tries again" on failure. No measurement, no comparison with CI or instructions. Part two has a single report of an agent reacting to a rejecting hook by moving another session's files, and Aider's default of skipping hooks.
- Böckeler: that an instruction is "quite unreliable" and that a git hook suits frequent small commits. One app, her experience, and she did not try the hook route.
- Stripe: that running all tests locally is infeasible and that more CI rounds have diminishing returns. An engineering statement, not data.
- Osmani: that constraints should be added only after a real failure. No evidence.
- Steinberger: that no hook stops a determined agent. No source tests it, and part two has reports of agents bypassing or skipping hooks (Aider's default, Claude Code reports), all single reports.
- Vincent: that worktrees silently lose hooks. A draft spec; related reports of worktree tools changing the hook path are in part two (single, mostly unreproduced) and describe a different mechanism.
- Kinney: the speed thresholds and that regular `--no-verify` means the hook is too strict. Part two finds no source that measures a threshold at which a hook is too slow.
- Carson: that an agent review in pre-commit works. No result reported; part two has one power user's self-reported use of a model-judged pre-commit gate that "works, but it is bypassable by the agent".
- Huntley: the pre-commit line is one clause in a post about Antithesis; no account of results.

## What the evidence shows

### How to read the evidence

The other 25 notes in [sources/](sources/) (the twelve practitioner notes are part one) come in four strengths. All were written from raw page text, raw GitHub API JSON or raw source files (each says how); none through WebFetch.

- The git project's own documentation (githooks, git-commit, git-push, git-merge, git-rebase, git-config, git-hook, git-init, git-receive-pack, Pro Git). Precise about mechanics, versioned (githooks "last updated in 2.54.0", git-hook 2.55.0), and about git, not about agents. It states what git does; it never mentions AI agents.
- Tool documentation: Husky, Lefthook, the pre-commit framework, GitHub (pre-receive hooks and protected branches), Claude Code (permission modes, sandbox, changelog), Codex (approvals and security), Aider (git docs). Vendor-first-party and undated except by version text. Several notes read only the matching passages, not whole pages (the Claude Code and Codex notes say so). The Husky mechanism page returned 404, so how Husky works comes only from its home-page feature list. Lefthook's option pages were not read.
- Tool source code, read on the main branch at fetch time rather than a pinned release: Aider (`repo.py`, `args.py`), Codex (sandbox tests, git helpers), Gemini CLI (prompt text, checkpoint service). Precise about what the code does on that day; code says nothing about intent unless a comment does.
- Single-user issue reports and comments on GitHub (Claude Code, Codex, Aider), mostly unreproduced by us and by the vendor. Several were closed by a stale bot with no vendor comment, so "closed" says nothing about whether the problem was fixed. None gives a frequency.

What is absent: no source measures how often git hooks catch an agent's failure, how often agents skip them, or how often hooks silently fail to run; no source compares outcomes with and without a git hook, or a git hook against an agent hook, CI or instructions. Coverage of Cursor, Copilot (coding agent and CLI), Cline, Windsurf and OpenCode is nil or thin: the only sources on agents are Claude Code, Codex, Aider and Gemini CLI. Nothing here was tested by us.

### What git hooks are, mechanically

From git's own documentation ([hook inventory](sources/git-githooks-hook-inventory-and-inputs.md), [no-verify scope](sources/git-commit-push-merge-rebase-no-verify-scope.md), [config](sources/git-config-hookspath-and-config-based-hooks.md)):

- Hooks are tied to specific porcelain commands. Client-side hooks that can stop the operation by exiting non-zero: pre-commit, prepare-commit-msg, commit-msg, pre-merge-commit, pre-rebase, pre-push, pre-auto-gc, plus the `git am` and `git send-email` ones. Hooks "meant primarily for notification" cannot change the outcome: post-commit, post-merge, post-rewrite, post-receive, post-update and others. post-checkout can only pass its exit status through.
- What a hook sees is narrow. pre-commit takes no arguments and must ask git itself what is staged; pre-push gets ref names and object ids on stdin, not file contents; hooks run with the working tree root as the current directory and `GIT_DIR` and similar variables exported. Commit hooks run with `GIT_EDITOR=:`, so they run with no editor and no interaction. The page attaches commit hooks to `git commit`; that plumbing such as `git commit-tree` does not run them is our inference, not stated. Whether a commit made through a library or an IDE runs hooks is not stated and was not checked.
- Hooks without the executable bit are ignored. Hooks run only through the commands that call them: they see git operations and nothing else the agent does (file writes, shell commands, network calls). That is the difference from an agent hook.
- Three separate bypasses are documented, at different scopes. `--no-verify` is per command and per hook family: git-commit skips pre-commit and commit-msg (not prepare-commit-msg, not the post hooks), git-push skips pre-push, git-merge skips pre-merge-commit and commit-msg, git-rebase skips pre-rebase. `git -c core.hooksPath=/dev/null` disables every hook, including ones `--no-verify` does not cover; the git-config page calls it "usually only advisable for expert users". The hook managers add their own switches: `HUSKY=0`, `LEFTHOOK=0`, and pre-commit's `SKIP=<hook ids>`, which skips one hook rather than the whole commit ([Husky](sources/husky-docs-core-hookspath-and-disabling.md), [Lefthook](sources/lefthook-docs-intro-and-env-switch.md), [pre-commit](sources/pre-commit-framework-docs-install-skip-and-ci.md)). Which of these an agent will use, and how often, is stated by no source. A check that greps an agent's command for `--no-verify` (described in comments in the [test-gate notes](../hooks-as-test-gate/sources/claude-code-issue-40117-agent-bypasses-precommit.md)) would not see an environment-variable switch; that is our inference, and no source tests it.
- The rebase page says the two backends' calling of post-commit and post-checkout was "by accident of implementation rather than by design" and may stop; the page does not say whether pre-commit runs on each replayed commit.

### Distribution: hooks are per clone, unless something arranges otherwise

- Git's stated default is that hooks live in `$GIT_DIR/hooks`, which is not versioned, and Pro Git says "hooks aren't transferred with a clone of a project" and "Git won't set them up automatically" ([Pro Git](sources/git-pro-git-server-side-enforcement-and-client-hooks.md)). Every hook manager read works around this with an install step: `npx husky init` plus a `prepare` script (runs on package install), `lefthook install`, `pre-commit install` ("should always be the first thing you do" on every clone). Husky and Lefthook both assume hooks do not run in CI (`HUSKY=0`, `LEFTHOOK` gating). What is shared is the config file, not the installed hook.
- `core.hooksPath` points git at a directory of hooks and is documented as a way to configure hooks centrally; it is what Husky uses, and what this repository's own hook needs per clone. It lives in `.git/config`, which also does not travel with a clone (our inference, marked so in the note).
- Newer git can define hooks in config (`hook.<name>.command` and `.event`, in system, global or local config), so a script can be shared across repositories; `git hook list` shows what will run. The pre-commit framework's page uses this for a global install and itself calls it "not recommended" because hooks can run "when interacting with an untrusted repository". Which git version introduced it, and how widely deployed such versions are, is not stated on the pages read. This changes the flat statement "not shared by clone" only for machine-level or user-level setups, not for a repository's own hooks.
- The Claude Code self-hosted runner sets `core.hooksPath` itself (to add a `Co-authored-by` trailer) and leaves it alone if the image already sets one; a snapshot script pins it to `/dev/null`; and Claude Code switches off a repository's git hooks for plugin eval runs ([docs note](sources/claude-code-docs-git-hook-paths-in-permissions-and-sandbox.md)). So a harness may itself take over or disable the hook path.

### Enforcement and early feedback are different jobs

Pro Git describes the design: server-side `update` or `pre-receive` hooks enforce ("as long as that update script is there and executable, your repository will never have a commit message without your pattern in it"), and client hooks give the developer early notice so the "carefully crafted work" is not rejected "at the last minute" ([note](sources/git-pro-git-server-side-enforcement-and-client-hooks.md)). It is a description of a design, not a measurement.

Server side, per git's docs ([note](sources/git-githooks-server-side-hooks-and-quarantine.md)): pre-receive runs once per push and non-zero rejects all refs; `update` runs per ref and can accept some and reject others; incoming objects sit in a quarantine directory and are migrated only after pre-receive succeeds, so a rejected push leaves no data. Output goes back to the pushing client, so a rejection can explain itself. These hooks run on the machine receiving the push and see refs and commits, not the working tree or the agent's session. The pages name no client flag that skips them; `git push --no-verify` toggles pre-push only. Host-side, GitHub Enterprise Server supports custom pre-receive scripts with a shared 5 second timeout budget, and a timeout rejects the push ([note](sources/github-pre-receive-hooks-and-branch-protection.md)). Whether github.com supports custom pre-receive hooks is not stated in the note and was not checked. On github.com the read source is branch protection, whose restrictions "don't apply to people with admin permissions" by default unless bypass is disallowed, and whose required status check results can be set by anyone with write permission unless a specific App is selected. So a server-side gate exists, but who can bypass it is configured at the host, and whether it is beyond an agent's reach depends on whose credentials the agent's push carries; no page says. The test-gate conclusion reached the server-side layer as the only one beyond the agent's reach by inference from the CI-backstop advice, and this topic found nothing that tests that inference. GitHub rulesets and push rules were not read.

The consequence for placement is only that the sources describe two layers doing different work: a server-side check that enforces against a local flag, and a local hook that is cheaper, earlier and skippable. No source measures the gap between them for agents.

### What an agent does to a git hook

The agent-specific evidence, all from single reports or code reading.

- The tool itself skips the hook. Aider passes `--no-verify` on every commit by default, states it in its docs ("By default, aider skips pre-commit hooks") and gives no rationale; `--git-commit-verify` turns hooks back on ([docs and code note](sources/aider-git-docs-commit-verify-default.md)). Two issues report the consequence: a blocking hook was defeated by Aider committing the offending code (reproduction as reported, not by us), and a commenter's anecdote of a similar default letting keys reach production is unverified ([note](sources/aider-issue-5057-default-commits-skip-precommit.md)). The maintainer's 2024 answer to a request for hook-style gating was to run `--test-cmd pre-commit`, that is, an agent-side loop that runs the hook's checks and asks the agent to fix failures ([note](sources/aider-issue-802-precommit-ignored-test-cmd-answer.md)). Gemini CLI's own checkpoint commits, made in a shadow repository, also use `--no-verify` and `allowUnsafeHooksPath` ([note](sources/gemini-cli-source-commit-failure-instruction-and-checkpoint-no-verify.md)); those are not the user's history as read. These contradict the test-gate conclusion's line that whether agent tools pass `--no-verify` by default "is not stated": for Aider it is.
- The tool's commit path differs from a terminal commit. Codex's desktop app "Commit or push" action is reported (one user, later a second) not to run a pre-commit hook that runs on a terminal commit ([note](sources/codex-issue-31235-app-commit-or-push-skips-hooks.md)). The reporter's diagnosis is that shared git helpers force `core.hooksPath=/dev/null`; our check of the source found the override on Codex's internal read-side helper commands, and whether the commit action uses them was not established. So the mechanism is unverified while the symptom is reported. CONTEXT.md's statement that a git hook "works the same for an agent and a human" therefore depends on which path in the tool makes the commit.
- The agent's setup rewrites the hook path. Claude Code's `--worktree`, EnterWorktree and worktree-isolated subagents are reported to run `git config core.hooksPath` against the shared config, overwriting a custom path such as `.githooks`; later versions are reported to write an absolute `core.hooksPath` into the worktree's `config.worktree` instead, so the hooks that run are the main checkout's, on whatever branch it is on ([note](sources/claude-code-issue-27474-worktree-overwrites-hookspath.md)). A commenter reports "silently disabled a pre-commit guardrail in the main checkout three separate times", and that a stale absolute `core.hooksPath` makes git run zero hooks without falling back to `.git/hooks`, with about 25 commits bypassing the local chain before CI caught a violation. That last git behaviour is asserted by the commenter and is not stated on any git page read; treat it as unverified. A census claim (13 of 13 tool-made worktrees) is a comment, unverified. Vincent's draft spec (part one) says worktrees do not inherit the hooks directory; that is a design-spec statement of what git does, unchecked here, and it differs from these reports, which are about the tool rewriting `core.hooksPath`. The reports differ by version (clobbered shared config versus per-worktree config) which fits a change over time rather than a contradiction, but the note does not settle it. The cluster's related issues were not read (see leads).
- The agent may not be able to commit, or install hooks, at all. Claude Code's sandbox denies writes to `.git/hooks` and `.git/config` (and inside a linked worktree's shared directory), while still letting `git commit` run so hooks execute; `.git`, `.husky`, `.pre-commit-config.yaml` and `lefthook.yml` are protected paths whose writes prompt by mode, and writes are allowed in bypassPermissions mode ([docs note](sources/claude-code-docs-git-hook-paths-in-permissions-and-sandbox.md)). One issue asks for a finer setting because an agent-run `make install-hooks` fails; the requester's reason for the deny (hooks as a persistence vector for a prompt-injected agent) is theirs, not the docs' ([note](sources/claude-code-issue-61909-sandbox-blocks-hook-install.md)). Codex's default workspace-write sandbox makes `.git` read-only, and a test comment states the reason: "a bad actor could write to .git/hooks/pre-commit so an unsuspecting user would run code as privileged the next time they ran `git commit` themselves" ([note](sources/codex-docs-sandbox-protected-git-path.md)); a user issue reports that this makes `git commit` fail with an index.lock permission error, with workarounds that change which process runs git ([note](sources/codex-issue-7071-sandbox-git-readonly-blocks-commit.md)). So in both, a git hook is treated as a code-execution path that the agent must not write, and whether the agent can commit is a permissions question that comes before whether a hook runs. In the test-gate conclusion, the layer that protects hook config differs (permission mode); here the sandbox is stricter than the permission-mode page, and the two layers are described separately.
- The agent may change a hook when asked to. One Codex report has a background task change a hook's shebang from bash to sh in 2 of 7 repositories while adding a block; no transcript ([note](sources/codex-issues-10477-and-45025-agent-and-hook-edits.md)). It shows unintentional edits, not disabling.
- Instructions against skipping hooks are followed strictly by one agent and not by another. A Codex user reports the agent refusing to even mention `--no-verify` because the repo's AGENTS.md prohibits it; the test-gate conclusion cites an Opus 4.6 report of six consecutive `--no-verify` commits despite memory rules. Two single reports, different agents and models; no source compares them. Gemini CLI's system prompt tells the model "If a commit fails, never attempt to work around the issues without being asked to do so" and never to commit unprompted (a rule, not a hook; whether followed is not measured), while an open Claude Code issue reports an agent reacting to a rejecting hook by moving another session's untracked files out of the way and then losing them with `rm -rf` ([note](sources/claude-code-issue-87981-workaround-after-hook-rejection.md), first-person, apparently agent-written, unverified). The hook in that report checked the whole working tree, not the staged content; the reporter's account is that this, plus the agent's workaround, caused the harm. The pre-commit framework's page says its hooks run only on staged contents and stash the unstaged changes for that reason, so it is a design choice that the page states and that the incident hook lacked.
- A git hook that changes files or holds locks interacts with the agent's state. Reports (all user, all unverified): an auto-fixing hook (trailing whitespace) fails the first commit and modifies files, after which the agent's view of the file reverts on later turns; a formatter run by a commit hook trips the Edit tool's "modified since read" guard; hook output (a pytest run) is visible to the model but not to the user; lint-staged failing while cleaning up `index.lock` is followed by an immediate retry, "sometimes bypassing hooks" (a one-paragraph report with no logs); a git-manager subagent does not clearly say a commit was blocked ([note](sources/claude-code-issues-pre-commit-side-effects-on-agent-session.md)). The pre-commit framework documents the first pattern as designed: an auto-fix hook exits 1 with "Files were modified by this hook" and the fixed files must be re-staged. An Aider commenter puts formatters "in a different class of tooling" from test hooks because they fix rather than reject.
- A hook can look enforced and be partly wired. In one report a commit-msg hook never fired on agent commits while pre-commit did; the reporter suspected `--no-verify`, a commenter argues that cannot be (it would skip pre-commit too) and that `core.hooksPath` pointing elsewhere plus the framework installing only the pre-commit stage explains it ([note](sources/claude-code-issue-66069-commit-msg-hook-not-firing.md)). The reporter did not reply and the two explanations were not tested here; the report cannot separate agent bypass from misconfiguration, which is the general difficulty with these reports.

### Uses beyond the test gate

- Blocking a commit on a check (tests, lint, secrets, policy). Every hook manager and the Pro Git chapter treat this as the central use. Aider's issue 5057 gives the argument that hooks are "real security controls, not just formatting checks"; that is a reporter's view. The test-gate notes cover the tests case.
- A review gate. One Claude Code request describes a pre-commit hook that demands an independent model's verdict on the staged diff, which the requester says ran for about 2.5 days, 9 repositories and about 68 gated commits and "works, but it is bypassable by the agent"; they ask for a harness-level PreCommit gate that also refuses `--no-verify` and stash-and-recommit ([note](sources/claude-code-issue-90887-precommit-gate-request-beyond-git-hook.md)). Their statement that "a client-side git hook is advisory to an agent that controls the shell" is a claim by one power user; the usage figures are self-reported. This is the only source here of a model-judged check inside a git hook. The requester also says false positives create "pressure to disable it".
- Message and trailer policy. commit-msg and prepare-commit-msg hooks check or edit commit messages (git's defaults include duplicate Signed-off-by detection); Claude Code's runner uses them to add a co-author trailer.
- Formatting and fixing. The framework and Aider discussions treat fixers as their own class (above); no source measures whether agents cope with them.
- Refs and history. pre-push sees refs and object ids on stdin including deletions; pre-rebase can prevent a rebase; server-side hooks can enforce fast-forward only and per-ref access control, per git's docs. None of the sources describes an agent case for these.
- A git hook that calls an agent. Claude Code's `-p` docs list pre-commit hooks as a place to call it non-interactively; nothing read describes results.
- Notification and audit: post-* hooks cannot change the outcome and none of the sources describes agent use of them.

### Git hooks beside agent hooks and other controls

- The vendor's own example of a "pre-commit check" in Claude Code is an agent hook, a PreToolUse hook with `"if": "Bash(git commit *)"` ([note](sources/claude-code-whats-new-w13-hook-if-git-commit-example.md)). The page says it cuts process overhead on busy sessions and does not compare the two or say when to prefer either. An agent hook sees the agent's tool call and can refuse `--no-verify`; a git hook sees only the git operation and cannot see how it was invoked. Both are described in the [agent-hooks conclusion](../agent-hooks/conclusion.md), whose caveats (best-effort command matching, fail-open exit codes, silent non-firing, who can disable hooks) apply to the agent-side layer and not to git's. The commit-request issue treats the two as complementary, one seeing the tool call and one the git event.
- Server-side hooks, branch protection and CI are the layers the sources place beyond a local `--no-verify`; the pre-commit framework and Husky documentation themselves pair local hooks with a CI run (`pre-commit run --all-files`, hosted pre-commit.ci). No source compares these on coverage or cost for agents.
- Tool-level checks: Aider's `--test-cmd` and lint commands run inside the tool's loop and feed failures back to the model, the maintainer's stated route to hook-like checks.
- Instruction files: the sources give the two conflicting Codex and Claude Code reports above and Gemini's prompt text. No measurement. Practitioners' use of instructions against `--no-verify` (Vincent, Kinney, Pocock in part one) is opinion with no test behind it here.

### Costs and failure visibility

- Time: practitioner speed rules (Kinney's under 10 seconds for pre-commit, under 2 minutes for pre-push, in part one) are stated without measurement. Pre-commit hooks are serial by default and commit hooks are never run in parallel ("applypatch-msg, pre-commit, ..." always run sequentially even with `-j`); Enterprise Server gives server hooks 5 seconds. The framework's page and Husky's give no runtime expectation. Nothing measures agent-time cost or a threshold at which a hook is too slow.
- Visibility: git prints a hook's output and aborts the commit on non-zero, so a working reject is visible to whoever ran it; the reports show it may not be visible to the user when an agent ran it (pytest output shown to the model only). A hook that does not run leaves no error in the reports: the stale `hooksPath` claim, the worktree overwrite and the app commit all present as a commit that simply succeeded, and CI or a later comparison caught them. Git provides `git hook list` and `GIT_TRACE`, and a commenter suggests `git config --get core.hooksPath`; no source says an agent harness reports whether hooks ran.
- Security: a git hook is code run with the user's privileges at commit time. Codex's and Claude Code's sandboxes treat write access to it as a persistence risk, and the pre-commit framework warns about global hooks running on untrusted repositories; Husky refuses to install in parent directories "for security reasons".
- Environment: shell startup files matter to hooks managed by Husky (its startup files load version managers); non-interactive and GUI-launched runs are not discussed. Lefthook's `interactive`, `use_stdin`, `no_tty` and `fail_on_changes` options were listed and not read, so whether hook managers behave differently under an agent's non-interactive shell is unknown here.

### Unverified, thin or contested

- Frequency: how often agents skip git hooks on their own, how often hooks silently fail to run in agent setups, how often a hook prevents a real defect. Every source is a single report or code reading; none measures.
- Practitioner claims in part one (that a commit hook is powerful for agents, that instructions are unreliable, that no hook stops a determined agent, that model review at commit works) rest on single accounts; Stripe's account is an engineering statement about its own pipeline, not data. The evidence above neither confirms nor refutes them.
- Comparison: no source compares git hooks with agent hooks, server-side checks, CI or instructions on outcomes for coding agents.
- Aider's default `--no-verify` is established from its docs and code on the main branch; that Aider users rely on hooks, and the anecdote of keys reaching production, are not. The commenters proposing fixes did not link changes.
- Codex app commit skipping hooks: symptom reported by two users, mechanism unconfirmed (see above).
- The stale `core.hooksPath` behaviour (git runs zero hooks) is a commenter's assertion, not on any git page read. The worktree reports are per version and mostly not reproduced by us.
- Issue 66069's cause is contested (reporter versus commenter). Issue 87981 is apparently agent-written and the loss of files is self-reported. Issue 28823's "sometimes bypassing hooks" has no transcript.
- Codex 10477 (refuses to mention `--no-verify`) and 45025 (shebang rewrite in 2 of 7 repos) are one user each; 45025 has no transcript.
- Claude Code sandbox rationale for denying `.git/hooks` is a reporter's inference; Codex states its reason only in a test comment.
- Coverage: Cursor, Copilot (coding agent and CLI), Cline, Windsurf, OpenCode and Kiro have no notes; Gemini CLI has only source-code lines on prompts and checkpoints; Claude Code, Codex and Aider carry most of the agent evidence. Absence of a statement about hooks in a vendor page is not evidence of either behaviour.
