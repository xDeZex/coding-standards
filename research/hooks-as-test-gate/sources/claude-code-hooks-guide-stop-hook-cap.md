# Claude Code hooks guide: Limitations, permission modes and the Stop block cap

Re-read pass 2026-09-26: whole guide page downloaded with curl as HTML, converted to text and read (Limitations, Hooks and permission modes, the `if` section, settings-location and troubleshooting sections read in full). Cross-checked against the raw hooks reference and the raw Claude Code CHANGELOG.md on GitHub. No summarising tool used. Companion to the reference note in this folder; complements (does not redo) research/testing-feedback-loop/sources/claude-code-hooks-as-test-gates.md.

- Troubleshooting entry "Stop hook hits the block cap": "Claude keeps working instead of stopping, then ends the turn with a warning that the Stop hook blocked too many consecutive times." Then: "Claude Code overrides a Stop hook after it blocks eight times in a row without progress. Your hook script needs to check whether it already triggered a continuation. Parse the stop_hook_active field from the JSON input and exit early if it's true", with a bash example (`jq -r '.stop_hook_active'`, then `exit 0 # Allow Claude to stop`, then a placeholder `# ... rest of your hook logic`). "If your hook legitimately needs more than eight iterations to converge, raise the cap with CLAUDE_CODE_STOP_HOOK_BLOCK_CAP." The example is generic, not a test gate. Our reading: exiting 0 whenever stop_hook_active is true means a hook written that way forces only one extra turn; the page does not say which to prefer for a test gate.
- Does progress reset the counter? Three Anthropic texts phrase the cap differently and none defines progress. Guide: "eight times in a row without progress". Reference (Stop input): "8-consecutive-continuation cap: after stop hooks have continued the turn eight times in a row". CHANGELOG entry in v2.1.143: "Fixed stop hooks that block repeatedly looping forever — the turn now ends with a warning after 8 consecutive blocks (override via CLAUDE_CODE_STOP_HOOK_BLOCK_CAP)". Unresolved from the texts; two of the three say "consecutive" with no qualifier. (Issue 55754 was filed against v2.1.126, before v2.1.143.)
- Limitations: command hooks communicate through stdout, stderr and exit codes only; PostToolUse cannot undo actions; Stop hooks "fire whenever Claude finishes responding, not only at task completion. They don't fire on user interrupts. API errors fire StopFailure instead."
- Permission modes: "PreToolUse hooks fire before any permission-mode check, in every permission mode, including dontAsk. A hook that returns permissionDecision: "deny" blocks the tool even in bypassPermissions mode or with --dangerously-skip-permissions." "Hooks can tighten restrictions but not loosen them past what permission rules allow."
- Can the agent change its own hooks mid-session? Page statements: /hooks "is read-only. To add, modify, or remove hooks, edit your settings JSON directly or ask Claude to make the change"; "If you edit settings files directly while Claude Code is running, the file watcher normally picks up hook changes automatically" (troubleshooting says restart the session if the watcher missed it); a ConfigChange event exists that can log or "block unauthorized modifications" of settings or skills files (exit 2 or `{"decision": "block"}`, not for policy_settings). Companion pages (permission-modes, read raw): `.claude` and `.git` and `.husky` are protected paths whose writes are prompted in default and acceptEdits mode, routed to the classifier in auto mode, denied in dontAsk mode and allowed in bypassPermissions mode; `permissions.allow` rules in settings do not pre-approve them. So the docs describe agent-driven hook edits as supported and live-reloaded, gated by permission mode. Not tested by us.
- `if` filter: the guide's worked example runs a hook only for `"if": "Bash(git *)"` with a script `check-git-policy.sh` (script body not shown; no commit or test check). "Because the filter is best-effort, use the permission system rather than a hook to enforce a hard allow or deny." Table rows: `npm test && git push` matches `Bash(git *)`; `$TOOL git push` runs the hook.
- Other hook types: prompt hook (type "prompt") is a single model call (Haiku by default, 30 s); on Stop it feeds the reason back unless the model returns "impossible": true. Agent hook (type "agent"): 60 s default, up to 50 tool-use turns, same ok/reason format, "experimental and may change" (reference).
- Multiple hooks on one event run in parallel. Shell-form command hooks run via `sh -c` (Git Bash or PowerShell on Windows); profile output that prepends text to stdout breaks JSON parsing and is silent on exit 0.
- Config sharing: `.claude/settings.json` "can be committed to the repo"; managed policy is admin-controlled; `disableAllHooks` is read after settings precedence, so a project file can override a user file, and it cannot disable managed hooks.

Not on the guide page: a worked example of a test-running Stop hook or a commit-gating PreToolUse hook.
