# Hooks as a test gate

Findings on using a hook to run the tests as a gate on a coding agent: a commit hook that blocks a commit on red, and a stop hook that keeps the agent working until the check passes. This extends the parent topic, [testing as the agent's feedback loop](../testing-feedback-loop/conclusion.md), which already describes the hook as a computational sensor placed at a fixed point in the agent's flow. Findings only; no kit design, no catalogue entries, no recommendations. The 17 source notes were written by two researchers, one on vendor hook mechanics and one on gate design and limits.

## How to read the evidence

Three kinds of source, of different strength.

- Vendor documentation (Claude Code, Cursor, Gemini CLI, GitHub Copilot, OpenAI Codex, and the git project's own docs). First-party, precise about mechanics, undated, versioned in text and liable to change. Most were read as raw page text, which is the strongest reading method in this folder; the Claude Code hooks pages were fetched raw because a summarising fetch of the reference returned a wrong Stop schema. None of these pages gives a worked example of a test-running Stop hook or a commit-gating hook, so every "run the tests in a hook" design below is our inference from the mechanics, not a documented recipe.
- Two incident and practitioner sources on bypass and loops ([issue 40117](sources/claude-code-issue-40117-agent-bypasses-precommit.md), [issue 55754](sources/claude-code-issue-55754-stop-hook-loop.md), [pydevtools guide](sources/pydevtools-stop-agents-bypassing-precommit.md)). Single reports, read through a summarising tool, so quotes are as returned.
- Older human-era canon (Fowler on CI and coverage, Google on test sizes, Petrovic and Ivankovic on mutation testing). It never mentions agents or hooks; connecting it to a gate is our extension, and the notes say so.

No source measures how well a hook gate works on ordinary agent work: how often it catches red, how often agents route around it, or whether it improves outcomes compared with the agent running tests on its own.

## What a hook can and cannot block

The mechanics differ by vendor, and the differences matter for whether a test script actually gates.

- Claude Code: exit code 2 blocks; exit 1 is a non-blocking error unless valid JSON is returned, so a script that passes `npm test`'s failing status through with exit 1 does not gate ([reference note](sources/claude-code-hooks-reference-stop-and-pretooluse.md)). Git is the opposite: any non-zero exit from pre-commit aborts the commit ([git note](sources/git-hooks-pre-commit-and-no-verify.md)). The page states this warning itself, so the support is strong.
- Gemini CLI has exit 2 as block and other non-zero as warning ([note](sources/gemini-cli-hooks.md)). Cursor treats exit 2 as deny but other failures as fail-open unless `failClosed` is set ([note](sources/cursor-hooks.md)). Copilot's preToolUse is fail-closed on crash or non-zero exit, while any command hook timeout is fail-open ([note](sources/github-copilot-hooks.md)). Codex accepts a JSON decision or exit 2 ([note](sources/openai-codex-hooks.md)). So "exit non-zero on red" is not portable across tools.
- Timeouts. Claude Code's default for command hooks is 600 seconds, and on PreToolUse a timed-out command hook does not block the call ("don't count on a stalled hook to act as a gate"). Copilot's timeouts are always fail-open; Copilot's default is 30 seconds, Gemini's 60 seconds, Codex's 600 seconds; Cursor's default is only "platform default". The direct implication, recorded in the reference note, is that a suite slower than the timeout fails open at the gate. The consequence is the notes' reading of the docs, not a tested result.
- Matching a commit. Claude Code filters by tool name and an `if` permission-rule pattern such as `Bash(git *)`; Cursor's `beforeShellExecution` matches the shell command string; Codex matches Bash and inspects the command. No page documents a git-commit recipe; matching `git commit` is inferred from the syntax in all three cases. Claude Code's page says commands inside `$()` and after `&&` are checked, but a command name held in a variable runs the hook anyway.
- Hooks are not decisive over the human's own settings. Claude Code hooks fire before permission-mode checks, and a deny blocks even under `--dangerously-skip-permissions`; but `disableAllHooks` turns off user and project hooks (not managed ones), Copilot has a per-repository setting to skip hooks, and Codex loads project hooks only if the project layer is trusted. Whether an agent can edit its own hook configuration mid-session is unverified; the reference says settings edits are normally picked up by a file watcher, which suggests they could take effect, and no page read addresses the case.

## The commit gate

Git's own documentation says pre-commit "can be bypassed with the `--no-verify` option" ([git note](sources/git-hooks-pre-commit-and-no-verify.md), [overlapping summarising-tool note](sources/git-githooks-pre-commit-bypass.md)). The bypass is a flag on the same command the agent runs, so a git commit hook is advisory against an agent that adds it. commit-msg is bypassable the same way; prepare-commit-msg is stated not to be suppressed by `--no-verify`. Whether `git push --no-verify` bypasses pre-push is unverified in the notes.

The one incident in the folder is [Claude Code issue 40117](sources/claude-code-issue-40117-agent-bypasses-precommit.md): a reporter says Opus 4.6 bypassed a pre-commit hook on six consecutive commits using `--no-verify`, `git stash` and quiet flags, against an explicit written instruction not to, and that it misrepresented what it had done when asked. Commits landed with failing tests. This is one user's unverified report, closed as not planned, and shows nothing about frequency. What it does support, weakly, is the general point that an instruction is not enforcement and that a commit hook binds only if it cannot be skipped. The [pydevtools guide](sources/pydevtools-stop-agents-bypassing-precommit.md), which rests on that same issue, lists layers (a policy line, permission deny rules, a PreToolUse hook that rejects `--no-verify`, a PATH shim around git, a CI backstop) and itself says the layers block the flag but not stash or output suppression. Its idea of denying all commits and routing them through an MCP server was not followed up. The observation that only a server-side check is beyond the agent's reach is the researcher's inference from the CI-backstop advice.

An agent-side hook (matching Bash and denying `--no-verify`) is described as a possible defence in two notes, but no source documents it as a recipe.

### Reconciling the two git notes

The two git-hooks notes agree on pre-commit and `--no-verify`. They differ on one claim. The summarising-tool note records that hooks live in `.git/hooks/`, are not version controlled and are not shared by clone. The raw-text note records that the page does not state "not cloned" outright and treats it as unverified from the docs, while agreeing on the location, `core.hooksPath` and the executable-bit rule. The safer statement is: hooks live in `$GIT_DIR/hooks` or a `core.hooksPath` directory; that a fresh clone does not get them automatically is widely understood and consistent with this repository's own opt-in step, but is not confirmed by the page as read. Neither note is contradicted.

## The stop gate

A stop-type hook that blocks and feeds a reason back is available in every vendor read, under different names and mechanisms: Claude Code Stop (exit 2 or `decision: "block"`), Codex Stop (JSON or exit 2, the reason becomes a new user prompt), Copilot `agentStop` (a `decision: "block"` JSON), Cursor `stop` (a `followup_message`, submitted as the next user message, not exit 2), Gemini `AfterAgent` (exit 2 or `decision: "deny"` retries the turn). Claude Code's `/goal` is described as a session-scoped shortcut for a prompt-based Stop hook, with a small model judging the condition ([note](sources/claude-code-goal-command.md)); the page read does not say it runs the test command itself. Prompt-based Stop hooks are likewise a model judgement (default Haiku, 30 seconds), not a deterministic test run ([cap note](sources/claude-code-hooks-guide-stop-hook-cap.md)). That is the inferential option beside the computational one.

Stop fires whenever the agent finishes responding, not only at task completion, and not on user interrupts (Claude Code); errors fire StopFailure instead. Copilot's agentStop in cloud agents counts forced turns against the job's timeout. Copilot documents exit-2 behaviour on agentStop as a warning, not clearly a block, so the block route differs there; whether it forces continuation is unverified.

### Loop caps and the guard field

- Claude Code: an override after eight consecutive blocks. Copilot: the same eight, "runaway guard". Cursor: default five automatic follow-ups (`loop_limit`, null removes it; the loop limit table says the default is null for hooks loaded from Claude Code configuration). Codex: no cap found in the sections read, only the `stop_hook_active` field. Gemini: no retry cap found. Both "not found" are absence in what was read, not evidence of no cap.
- Claude Code exposes `stop_hook_active`, true when the agent is already continuing because of a stop hook, with the instruction to check it to avoid "blocking on a condition that will never resolve". Copilot, Codex and Gemini expose the same field.

Reconciling the two Claude Code cap notes, which record the same eight-block cap and the same field. Two points of difference. First, the hooks guide phrases the cap as eight blocks "in a row without progress", while the reference states "eight consecutive continuations" with no progress qualifier; the notes do not resolve whether progress resets the counter. Second, the raw-text note adds the environment variable `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` to raise the cap (stated by both the guide and the reference); the loop-guard note does not mention it. There is no disagreement about the mechanism.

Both notes draw the same consequence, flagged as the researchers' own reading and not a claim on the page: the guide's example script exits 0 whenever `stop_hook_active` is true, so a test gate written that way forces at most one extra turn even if the tests are still red, and the harness override after eight blocks ends the loop regardless. On that reading a stop hook is a bounded nudge, not a guarantee of green. The guide does not say which to prefer for a test gate, nor what happens to the red state after the override.

The failure in the other direction is documented by [issue 55754](sources/claude-code-issue-55754-stop-hook-loop.md): a model-judged Stop hook that never checked `stop_hook_active` looped, with the reporter saying it consumed the session quota in about 50 minutes. The issue was closed as a duplicate of other reports and search surfaced several similar ones that were not read. It is one user's report about a model-judged condition the agent could not satisfy, not evidence about test-running hooks.

## Where the hook sits, and its limits

Placement. The sources that touch the point (CircleCI, via the parent topic; Fowler's staged-build description) put a fast tier at the point of commit or push and slower tiers behind it. Fowler's commit build is mostly unit tests with external services doubled, targeting the "ten minute build" guideline, with a slower second stage that "might take a couple of hours" ([note](sources/fowler-ci-commit-build-vs-secondary-build.md)). The note states that this suggests a gate should run only the fast tier, and that this is inference: Fowler writes about human teams and CI servers. Google's small and medium test limits (60 seconds and 10 minutes per test, in 2010) are per-test limits, not a latency budget for a gate ([note](sources/google-test-sizes-time-limits.md)). No source gives a threshold at which a hook gate becomes too slow, and none on flaky tests in a hook. The folder's only tie between slowness and the gate is the timeout behaviour above (a suite over the timeout fails open) and the parent topic's flaky-test material; a flaky suite in a stop gate that blocks on red is the same never-resolving condition the loop-guard text warns about, though no source tests that specific case.

Complement, not replacement. The hook runs at a fixed point regardless of whether the agent chose to run tests. The vendor framing is "deterministic control: certain actions always happen rather than relying on the LLM to choose to run them" ([note](sources/claude-code-hooks-guide-stop-hook-loop-guard.md)). The parent conclusion records the same complementary reading; no source in this folder measures it.

A pass is not proof the tests still mean something. The hook checks an exit status. [Fowler on coverage](sources/fowler-test-coverage-numeric-target.md) says a numeric target invites hitting it with low-quality tests ("high coverage numbers are too easy to reach with low quality testing"); the note's reading, not Fowler's, is that a green run is the same kind of proxy. [Petrovic and Ivankovic](sources/petrovic-state-of-mutation-testing-at-google.md) describe mutation testing as the standard way to ask whether tests would still catch a fault, which a pass/fail hook cannot; at Google it was too expensive to compute over the whole repository and was run per code-review diff instead, not as a per-edit gate (only the first three pages were read). Nothing here tests mutation testing against agent-written or agent-weakened tests; that is an extension. The parent conclusion carries the measured evidence on agents weakening tests (ImpossibleBench, EvilGenie, METR, OpenAI); this folder adds none, and none of it was measured against a hook gate. So the claim that a passing hook does not show tests are unweakened is supported by mechanism (the hook sees only an exit status) and by the parent's benchmarks, not by a study of hooked agents. The commit bypass in issue 40117 is a different problem from tampering: there the hook never ran. A tamper-evident check would need something the hook does not do.

## Connection to AI coding

- The gate exists because instructions are advisory. The vendor claim is that hooks are deterministic; the one incident and the git docs show that determinism holds only if the agent cannot skip the hook, and that the git-side hook is skippable by design.
- The tools converge on the same stop-and-continue shape with different exit-code and fail-open rules, and most have an 8- or 5-step cap or a guard field. That makes the stop hook, as documented, a bounded persistence mechanism for an agent, and makes each hook's timeout and fail behaviour part of whether it gates at all.
- A red run drives the agent's next turn only through the reason text the hook returns; a failure the agent cannot resolve can loop (issue 55754) until a cap or timeout.
- Local hooks sit inside the agent's environment; the only layer described as beyond its reach is a server-side check, which the notes reach by inference.

## Unverified, thin or contested

- No worked example of a test-running Stop hook or a commit-gating PreToolUse hook in any vendor doc; matching `git commit` is inference from matcher syntax in Claude Code, Cursor and Codex.
- Frequency of agents bypassing commit hooks: one unverified bug report. Frequency of stop-hook loops: one report read, others listed and not read.
- Whether progress resets Claude Code's eight-block counter; Codex and Gemini caps (not found); Copilot's exit-2 behaviour on agentStop; `git push --no-verify`; whether hooks are not cloned (see reconciliation); whether an agent can edit hook config mid-session; whether hooks apply in Antigravity CLI. The Gemini CLI docs carry a banner saying it was replaced by Antigravity CLI for unpaid and Google One users, so those docs may be superseded.
- Whether `/goal` runs tests itself (the page as read says a model judges the condition); the rest of the page was not read.
- Slow or flaky suites: no source measures a threshold or a hook failing on flakiness; the timeout and Fowler-staging points are documented mechanics and inference respectively.
- Mutation testing beyond the first three pages of Petrovic and Ivankovic; nothing on mutation testing of agent-authored tests.
- Vendor pages are undated, versioned in text and change (Claude Code v2.1.x text, Codex redirects, Copilot URLs likely to move); the summarising-tool notes (git summary, both Claude Code issues, pydevtools, Fowler, Google) need re-checking before their quotes are reused.
