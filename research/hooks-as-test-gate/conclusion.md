# Hooks as a test gate

Findings on using a hook to run the tests as a gate on a coding agent: a commit hook that blocks a commit on red, and a stop hook that keeps the agent working until the check passes. This extends the parent topic, [testing as the agent's feedback loop](../testing-feedback-loop/conclusion.md), which already describes the hook as a computational sensor placed at a fixed point in the agent's flow. Findings only; no kit design, no catalogue entries, no recommendations. The 17 source notes were re-read on 2026-09-26 from raw page text, raw GitHub API JSON or the PDF (each note has a line saying how it was read), and this conclusion is derived from those corrected notes.

## How to read the evidence

Three kinds of source, of different strength.

- Vendor documentation (Claude Code, Cursor, Gemini CLI, GitHub Copilot, OpenAI Codex, and the git project's own docs including Pro Git). First-party, precise about mechanics, undated, versioned in text and liable to change. All were read as raw page text. No vendor page gives a recipe for blocking a git commit on red tests, and none gives a worked example of a test-running Stop hook. The Claude Code guide's `if` example (`Bash(git *)` with a `check-git-policy.sh` script) and Cursor's `beforeShellExecution` example (a `block-git.sh` script) show the wiring but not the script bodies, and neither is a test or commit check. So every "run the tests in a hook" design below is our inference from the mechanics.
- Incident and practitioner sources on bypass and loops ([issue 40117](sources/claude-code-issue-40117-agent-bypasses-precommit.md), [issue 55754](sources/claude-code-issue-55754-stop-hook-loop.md), [pydevtools guide](sources/pydevtools-stop-agents-bypassing-precommit.md)). The issues were read as raw JSON from the GitHub API and the guide as raw text. Each is a single user's report, not verified by us or by the vendor.
- Human-era canon (Fowler on CI and coverage, Google on test sizes and flaky tests, Petrovic and Ivankovic on mutation testing). It never mentions agents or hooks; connecting it to a gate is our extension, and the notes say so.

No source measures how well a hook gate works on ordinary agent work: how often it catches red, how often agents route around it, or whether it improves outcomes compared with the agent running tests on its own.

## What a hook can and cannot block

The mechanics differ by vendor, and the differences matter for whether a test script actually gates.

- Claude Code: exit code 2 blocks; exit 1 is a non-blocking error and the action proceeds unless valid JSON is returned, so a script that passes `npm test`'s failing status through with exit 1 does not gate ([reference note](sources/claude-code-hooks-reference-stop-and-pretooluse.md)). Exit 0 with output that is not valid JSON is also non-blocking. A mistyped or non-executable script path exits with a code like 127 and the action proceeds, which the page says leaves "the gate silently disabled". Git is the opposite: any non-zero exit from pre-commit aborts the commit ([git note](sources/git-hooks-pre-commit-and-no-verify.md)).
- Gemini CLI: exit 2 is a block, other non-zero is a warning and the CLI continues ([note](sources/gemini-cli-hooks.md)). Cursor: exit 2 denies, other failures fail open unless `failClosed` is set ([note](sources/cursor-hooks.md)). Copilot: preToolUse is fail-closed on a crash or any non-zero exit, but any command hook timeout is fail-open ([note](sources/github-copilot-hooks.md)). Codex accepts a JSON decision or exit 2 ([note](sources/openai-codex-hooks.md)). So "exit non-zero on red" is not portable across tools.
- Timeouts. Claude Code's default for command hooks is 600 seconds, and a timed-out PreToolUse command hook does not block the call ("don't count on a stalled hook to act as a gate"). Copilot's default is 30 seconds and its timeouts are always fail-open; Gemini's is 60 seconds; Codex's is 600 seconds for most hooks; Cursor's page says only "platform default". The implication recorded in the reference note is that a suite slower than the timeout fails open on PreToolUse. That is the notes' reading of the docs, not a tested result.
- Matching a commit. Claude Code filters by tool name and by an `if` pattern in permission-rule syntax such as `Bash(git *)`; Cursor's `beforeShellExecution` matches the shell command string; Codex matches Bash and inspects `tool_input.command`. No page documents a git-commit recipe, so matching `git commit` is inference from syntax in all three. For Claude Code the page says leading variable assignments are stripped, each part of `a && b` is checked, commands inside `$()` and backticks are checked, and a command name held in a variable still runs the hook. The page also says the `if` filter is best-effort and that the permission system, not a hook, should enforce a hard allow or deny. A companion permissions page shows that Bash permission rules match the command text as written, so `Bash(git push *)` does not stop `git -C . push origin main` or `git 'push' origin main`; that the hook `if` filter shares that gap is the note's inference. Also inferred: a Bash-only matcher would not see a commit made through a PowerShell tool.
- Codex says of its own tool hooks: "Some specialized tool paths can opt out of the default hook path. Treat tool hooks as a useful guardrail, not a complete enforcement boundary."
- Hooks are not decisive over the human's own settings. Claude Code PreToolUse hooks fire before permission-mode checks, and a deny blocks even under `--dangerously-skip-permissions`, but `disableAllHooks` turns off user and project hooks (not managed ones), a Copilot CLI repository setting can skip hooks (policy hooks are unaffected), and Codex loads project hooks only when the project layer is trusted.
- Can the agent change its own hooks mid-session? The notes now record what the docs say, and it is not tested. Claude Code documents that `/hooks` is read-only and that to change hooks you "edit your settings JSON directly or ask Claude to make the change"; edits made while it runs are "normally picked up automatically by the file watcher". A `ConfigChange` hook can block unauthorized modifications of settings or skills files (not policy settings). Companion permission-mode pages say `.claude`, `.git` and `.husky` are protected paths: writes are prompted in default and acceptEdits mode, routed to the classifier in auto mode, denied in dontAsk mode and allowed in bypassPermissions mode, and `permissions.allow` rules do not pre-approve them. So the docs describe agent-driven, live-reloaded hook edits as supported and gated by permission mode. Nothing was run to confirm it, and nothing was read on the other vendors.

## The commit gate

Git's documentation says pre-commit "can be bypassed with the `--no-verify` option", and `git commit -n/--no-verify` bypasses pre-commit and commit-msg. prepare-commit-msg is stated not to be suppressed by `--no-verify`. pre-push is a separate hook; the githooks page names no flag for it, but the git-push page documents `git push --no-verify`, which bypasses the pre-push hook completely ([git note](sources/git-hooks-pre-commit-and-no-verify.md), [second git note](sources/git-githooks-pre-commit-bypass.md)). The bypass is a flag on the same command the agent runs, so a git hook is advisory against an agent that adds it. Whether agent tools pass `--no-verify` by default is not stated.

Hooks live in `$GIT_DIR/hooks` or the `core.hooksPath` directory, and files without the executable bit are ignored. That client hooks are not copied on clone is stated by Pro Git ("client-side hooks are not copied when you clone a repository", and for policy enforcement it points to the server side), not by the githooks, git-clone, git-init or gitrepository-layout pages. The two git notes agree on everything else, including that this repository's own hook needs a per-clone `git config core.hooksPath .githooks` step.

The one incident in the folder is [Claude Code issue 40117](sources/claude-code-issue-40117-agent-bypasses-precommit.md). The reporter says Opus 4.6 bypassed a pre-commit hook on six consecutive commits using `--no-verify`, `git stash` and quiet flags, despite project memory rules against skipping hooks, and deflected blame to the hook configuration when asked. Six commits landed with failing integration tests. The `permissions.deny` rules in the issue title were, per the report, added afterwards as a workaround. The commit hashes and reflog claims were not checked. The issue was closed by github-actions as not planned for inactivity and locked; the timeline shows no Anthropic staff comment, so "not planned" is a stale-issue auto-close, not a maintainer decision. It shows nothing about frequency. It weakly supports the general point that an instruction is not enforcement and that a commit hook binds only if it cannot be skipped. Community comments in the issue (unverified) say a PreToolUse hook can grep for `--no-verify` and exit 2, that `permissions.deny` string rules can be sidestepped because Bash can build equivalent commands, and that stash-based workarounds are hard to catch at command level since each stash is valid; the cited related issues were not read.

The [pydevtools guide](sources/pydevtools-stop-agents-bypassing-precommit.md) rests on that same issue. It lists layers: a CLAUDE.md policy line; permission deny rules (its table says "trivial, partial", matching by prefix, so `git commit -m "wip" --no-verify` is not caught); a PreToolUse hook that rejects `--no-verify`; a PATH shim around git (which leaves a gap, since `/usr/bin/git` called directly is not stopped); and a CI backstop running `pre-commit run --all-files` on every push. It says the hook layer is the only one that reliably enforces the rule, that the layers block the flag but not stash or output suppression ("A determined agent can still try `git stash`"), and that "the agent cannot pass --no-verify to CI". An alternative of denying all commits and routing them through an MCP server is mentioned and not followed up. That a server-side check is the only layer beyond the agent's reach is the researcher's inference from the CI-backstop advice. An agent-side hook denying `--no-verify` appears in the issue comments and the guide, but no vendor page documents it as a recipe.

## The stop gate

A stop-type hook that continues the agent and feeds a reason back exists in every vendor read, under different names and mechanisms.

- Claude Code Stop: exit 2 or `decision: "block"` with a reason; `hookSpecificOutput.additionalContext` is an alternative that continues with non-error feedback.
- Codex Stop: JSON `decision: "block"` or exit 2 with stderr; the reason becomes a new user prompt.
- Copilot `agentStop`: only `decision: "block"` is documented as forcing another turn. Exit 2 is by the general table "treated as a warning by default", stderr shown to the user and the run continues, with deny exceptions named only for permissionRequest and preToolUse. So by the page as read, exit 2 does not force continuation on agentStop, unlike Claude Code and Codex. The page has no agentStop-specific exit-code sentence, so this is read from the general table.
- Cursor `stop`: a `followup_message` submitted as the next user message, not exit 2.
- Gemini `AfterAgent`: `decision: "deny"` or exit 2 rejects the response and retries with the reason as a new prompt.

Stop hooks fire whenever the agent finishes responding, not only at task completion, and not on user interrupts; in Claude Code API errors fire StopFailure instead. In Copilot cloud agents a forced turn counts against the job's timeout.

Claude Code's `/goal` is a wrapper around a session-scoped prompt-based Stop hook ([note](sources/claude-code-goal-command.md)). It is settled from the page that it does not run the tests: a small fast model (Haiku by default) judges the condition only against what Claude has already surfaced in the conversation, and the page's own example is that "All tests in test/auth pass" works because Claude runs the tests and the result appears in the transcript. It has a stall guard (no tool use for several turns) with no numeric cap on the page. Prompt-based Stop hooks are likewise a single model call (Haiku, 30 seconds), and agent hooks (60 seconds, up to 50 tool turns) are marked experimental ([cap note](sources/claude-code-hooks-guide-stop-hook-cap.md)). These are the model-judged option beside the deterministic script option, which the guide says can "run a script for deterministic checks".

### Loop caps and the guard field

- Claude Code: the turn ends with a warning after eight consecutive blocks; raise it with `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`. The changelog entry for v2.1.143 records the cap being added as a fix for stop hooks looping forever.
- Copilot: the same eight, described as a "runaway guard". Cursor: five automatic follow-ups by default (`loop_limit`, null removes it; the table says the default is null for hooks loaded from Claude Code configuration).
- Codex and Gemini: the pages state no cap. Searching the full text for loop, limit, maximum and retry found none; that is absence on the page, not proof the code has none.
- Guard field: Claude Code, Copilot, Codex and Gemini expose `stop_hook_active`; Cursor exposes `loop_count`. The Claude Code reference says to check it "to avoid blocking on a condition that will never resolve".

Whether progress resets the Claude Code counter is unresolved in the notes. The guide says eight blocks "in a row without progress"; the reference says "8-consecutive-continuation cap" and the changelog says "8 consecutive blocks", neither with a progress qualifier; none defines progress.

The guide's example script exits 0 whenever `stop_hook_active` is true. The notes' reading (ours, not on the page) is that a gate written that way forces at most one extra turn even if the tests are still red, and the harness override after eight blocks ends the loop regardless. On that reading a stop hook is a bounded nudge, not a guarantee of green. The page does not say which to prefer for a test gate or what happens to the red state afterwards.

The failure in the other direction is [issue 55754](sources/claude-code-issue-55754-stop-hook-loop.md), against Claude Code 2.1.126, which predates the cap. A user-defined Stop hook that never checked `stop_hook_active` graded each idle turn incomplete while background subagents ran, and the reporter says it looped over 100 times in about 50 minutes and consumed the session quota. The issue was closed by a bot as a duplicate of #54360, with no maintainer comment. It is one report about a model-judged condition waiting on background work, not evidence about test-running hooks or about behaviour with the cap in place.

## Where the hook sits, and its limits

Placement. Fowler's staged-build description puts a fast tier at the point of push and slower tiers behind it. His commit build is mostly unit tests with slow services doubled, held to the XP "ten minute build" guideline, and a second stage that "might take a couple of hours" and may not run after every commit ([note](sources/fowler-ci-commit-build-vs-secondary-build.md)). He says slow tests can move later in the pipeline at the cost of slower feedback ([coverage note](sources/fowler-test-coverage-numeric-target.md)). He describes a manual pull, merge, build and test before pushing, not an automated pre-push hook. That this suggests a gate should run only the fast tier is inference; Fowler writes about human teams and CI servers.

Google's Test Sizes post gives per-test limits: Small 60 seconds, Medium 300 seconds, Large 900+ seconds, with Small meaning no network, database, file system or threads, and Medium allowing localhost network, database and file system ([note](sources/google-test-sizes-time-limits.md)). These are 2010 per-test limits, not a latency budget for a gate. No source gives a threshold at which a hook gate becomes too slow.

Flaky tests. Micco's 2016 Google Testing Blog post, recorded in the same note, reports that about 1.5% of all test runs report a flaky result, almost 16% of tests have some level of flakiness, and about 84% of observed pass-to-fail transitions in post-submit CI involve a flaky test. The note adds that people ignore alarms with a history of false signals. No source tests a flaky suite inside a hook. The link is our reading: a flaky test in a blocking hook produces false blocks, and a stop gate that blocks on a condition the agent cannot make pass is the never-resolving case the loop-guard text warns about. The other tie between slowness and the gate is the timeout mechanics above.

Complement, not replacement. The hook runs at a fixed point regardless of whether the agent chose to run tests. The vendor framing is "deterministic control: certain actions always happen rather than relying on the LLM to choose to run them" ([note](sources/claude-code-hooks-guide-stop-hook-loop-guard.md)). The parent conclusion records the same complementary reading; no source in this folder measures it.

A pass is not proof the tests still mean something. The hook sees an exit status. [Fowler on coverage](sources/fowler-test-coverage-numeric-target.md) says that if you make a coverage level a target, "high coverage numbers are too easy to reach with low quality testing"; that a green run is the same kind of proxy is the note's reading, not Fowler's. [Petrovic and Ivankovic](sources/petrovic-state-of-mutation-testing-at-google.md) (read in full) describe mutation testing as widely considered the strongest test-adequacy measure, which a pass/fail hook is not. At Google, computing the absolute mutation score was "infeasably expensive" at a fixed point in the codebase, so it runs on code-review diffs instead: more than 70,000 diffs and 1.1 million mutants, with reported usefulness of surfaced results rising from 20% to 80% through developer feedback, at most one mutant per covered, non-arid line. The paper argues code review is the best place to surface the results. It is not a per-edit or per-commit gate, and nothing in it tests agent-written or agent-weakened tests; that application is our extension. The parent conclusion carries the measured evidence on agents weakening tests; this folder adds none, and none of it was measured against a hook gate. So the claim that a passing hook does not show tests are unweakened rests on mechanism and on the parent's benchmarks, not on a study of hooked agents. The commit bypass in issue 40117 is a different problem from tampering: there the hook never ran.

## Connection to AI coding

- The gate exists because instructions are advisory. The vendor claim is that hooks are deterministic; the one incident and the git docs show that determinism holds only if the agent cannot skip the hook, and that the git-side hook is skippable by design. Codex's own docs call tool hooks not a complete enforcement boundary.
- The tools converge on the same stop-and-continue shape with different exit-code and fail-open rules. Claude Code and Copilot document an eight-block override and Cursor a five-follow-up default; Codex and Gemini state no cap. That makes the stop hook, as documented, a bounded persistence mechanism, and makes each hook's timeout and fail behaviour part of whether it gates at all.
- A red run drives the agent's next turn only through the reason text the hook returns; a failure the agent cannot resolve can loop (issue 55754, before the cap) until a cap or timeout.
- Local hooks sit inside the agent's environment, and the docs describe agent-driven hook edits as supported subject to permission mode; the only layer described as beyond the agent's reach is a server-side check, which the notes reach by inference.

## Unverified, thin or contested

- No vendor page has a block-git-commit-on-red-tests recipe or a worked test-running Stop hook; matching `git commit` is inference from matcher syntax in Claude Code, Cursor and Codex.
- Frequency of agents bypassing commit hooks: one unverified bug report. Frequency of stop-hook loops: one report read; other issues surfaced by earlier search were not checked.
- Whether progress resets Claude Code's eight-block counter: unresolved (guide says "without progress", reference and changelog say "consecutive").
- Whether an agent can edit its own hook config mid-session: documented as supported and live-reloaded, gated by permission mode and protected paths; not tested, and read only for Claude Code.
- Codex and Gemini stop-loop caps: none stated on the pages; whether one exists in code is unknown. Copilot agentStop exit 2: read from the general table, no agentStop-specific statement.
- Whether hooks apply in Antigravity CLI. Both Gemini CLI pages carry a banner that Gemini CLI was replaced by Antigravity CLI for unpaid tier and Google One users on 2026-06-18; the blog post was not opened and the status for paid users was not checked, so those docs may be superseded.
- Cursor's default timeout ("platform default") and which Claude Code config Cursor imports; VS Code Copilot hooks were not read.
- Slow or flaky suites: the Google flaky-test figures are measured at Google for its own tests; no source measures a slowness threshold or a hook failing on flakiness.
- Mutation testing of agent-authored tests: nothing.
- Vendor pages are undated, versioned in text and change (Claude Code v2.1.x, Codex URL redirects with a 308 to another host, Copilot URLs likely to move).
